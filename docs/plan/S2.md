## 0. Objetivo y puerta de salida

**Objetivo:** un corte vertical completo — subir audio → transcribir → cleanup verificado →
índice híbrido → chat con citas — funcionando de punta a punta con evidencia.

**Puerta de salida — el sprint NO cierra sin todo esto:**

1. E2E real navegador → proxy → servicios con una clase sintética de 1 h generada en RAM y
   el límite efectivo publicado en `/ingestion/capabilities`.
2. Audio ausente (disco, Redis, logs, trazas, cachés) **antes** de indexar: la indexación
   solo ve texto.
3. Chat responde con citas válidas y con historial persistente (conversaciones/mensajes,
   `client_message_id` idempotente, cancelación de streaming).
4. G1, G2-T **o** G2-X, G3, G4 y G5-F1 aprobadas con evidencia: no persistencia,
   aislamiento, recuperación de transcript/índice/chat y métrica por idioma.
5. G4 publica por idioma numerador/denominador, partición de dataset y fórmula: Recall@8
   ≥ 0.85 (respondibles), precisión de citas ≥ 0.95, abstención ≥ 0.90; p95 de
   recuperación ≤ 500 ms y primer token p95 ≤ 5 s.
6. **D3-Texto cerrada** para el proveedor/modelo de embeddings y LLM antes de indexar o
   enviar el primer transcript no sintético; `P-S2-JL-10` registra el contrato real y los
   E2E/datasets de S2 usan texto sintético o redactado.

Regla dura: si D3-Texto sigue `pending|blocked`, S2 puede desarrollar y medir con texto
sintético, pero no procesar transcripts de clases reales.

**Interfaces congeladas el lunes:** shape final de chunks/embeddings y `index(audio_id)`;
SSE de chat `snapshot|delta|citation|done|error` con IDs monotónicos y terminal único;
formato de citas `[Materia · Clase · mm:ss]`; contrato paginado de `/search`.

## 1. Contratos congelados (referencia exacta)

### 1.1 Chunking y embeddings (proveedor: RAG · consumidor: Infra)

- Chunk objetivo **~800 tokens** con overlap **~100**, cortes en límites de frase/segmento;
  offsets Unicode `[inicio, fin)` preservados (emoji, acentos, CJK cuentan como 1); tabla
  `chunk_segments` enlaza chunk ↔ segmentos con rango de caracteres.
- Versionado de embeddings: cada `index_version` registra modelo, dimensión y versión;
  una generación nueva se construye completa y se **activa atómicamente**; jamás se mezclan
  modelo/dimensión/versión en el mismo índice activo.
- Evento `index(audio_id)`: job idempotente, consume shape congelado de outbox (`type:
  index.requested`, solo IDs); doble entrega → un solo índice; sin versiones parciales
  activas.

### 1.2 Eventos SSE del chat (proveedor: RAG · consumidores: Web, API)

```text
event: snapshot → {"message_id", "status":"streaming"}
event: delta    → {"text": "…"}
event: citation → {"index": 1, "audio_id", "transcript_version", "chunk_id",
                   "segment_id", "t_start", "t_end", "label", "url"}
event: done     → {"message_id", "conversation_id", "status", "sources"}
event: error    → {"code", "message"}   # p. ej. insufficient_evidence
```

Todos con `id:` monotónica; después de `snapshot` hay cero o más `delta|citation` y exactamente
un `done|error`. Las citas solo referencian **IDs validados en BD**; sus marcadores quedan en
buffer hasta validar. Sin offsets fiables la etiqueta es «segmento N», nunca un minuto
inventado. `message_sources` persiste **todas** las fuentes entregadas al modelo. Sin evidencia
suficiente hay abstención. El POST se consume con `fetch`; al reconectar se consulta el mensaje
persistido y un `client_message_id` repetido nunca reejecuta el modelo.

### 1.3 Contrato `/search` (proveedor: RAG+API · consumidor: Web/Ctrl+K)

`GET /search?q=&subject_id=&from=&to=&limit=&cursor=` → `{"results": [{"chunk_id", "audio_id",
"subject", "class_date", "snippet", "segment_id", "t_start", "t_end", "score_rrf"}],
"took_ms"}`. Ambas ramas (FTS por idioma + pgvector) filtran **primero** `user_id`, recursos
activos, versión activa y filtros — nunca top-k global y filtro después. Sin offsets
fiables, `t_start/t_end` null. Objetivo p95 ≤ 500 ms medido.

## 2. Tickets RAG (`L2.x`)

### L2.1 — Chunking con offsets Unicode

**Depende de:** L1.4 (contrato), tablas A2.1 · **Tests:** U-S2-JL-01.

Cómo debe funcionar: segmentador que toma transcript+segmentos y produce chunks según
§1.1; cortes preferentes en límites de frase y de segmento ASR; cada chunk guarda
`audio_id`, `transcript_version`, offsets de carácter sobre el texto completo, y sus filas
en `chunk_segments`. Casos de test obligatorios: emoji, acentos, CJK, cortes exactos en
frontera de frase, chunk final corto.

### L2.2 — Embeddings versionados + HNSW

**Depende de:** A2.1 · **Tests:** U-S2-JL-02, P-S2-JL-10.

Cómo debe funcionar: embedding batch de chunks con la dimensión/modelo registrados;
índice HNSW coseno; generación de índice nueva (`index_version`) construida al completo y
activada con una única transacción/UPDATE atómico — nunca hay momentos con mezcla de
versiones activas. `P-S2-JL-10` valida el contrato real del proveedor (dimensiones, cuotas,
límites) y alimenta la decisión D5. Antes de indexar texto de clases reales, D3-Texto debe
estar cerrada para ese modelo/proveedor (ver §0.6); con la decisión abierta solo se indexa
texto sintético o redactado.

### L2.3 — Búsqueda híbrida con filtros en ambas ramas

**Depende de:** A2.1 · **Tests:** U-S2-JL-03/04.

Cómo debe funcionar: rama lexical `tsvector` con configuración por idioma
(spanish/english/simple); rama vectorial pgvector coseno; fusión RRF determinista (mismo
input → mismo output, `k` documentado); dedupe y diversidad antes del top-k. Filtros
`user_id`/versión/tombstone aplicados **en ambas ramas antes del top-k** (G3). Casos: corpus
redactado, tombstone excluido, versión antigua excluida.

### L2.4 — `SearchService` + `GET /search`

**Depende de:** L2.3 · **Tests:** I-S2-JL-06 (en pareja con A2.11).

Cómo debe funcionar: servicio reutilizable (lo consume chat y el endpoint); params del
§1.3; snippet con contexto del match; timestamp del segmento si es fiable. Integración
contra Postgres+pgvector reales con corpus de prueba.

### L2.5 — Pipeline de chat SSE

**Depende de:** L2.4 · **Tests:** I-S2-JL-07/08.

Cómo debe funcionar, en orden: (1) embedding de la pregunta; (2) ~30 candidatos por rama;
(3) RRF; (4) dedupe + diversidad; (5) ~8 chunks finales bajo presupuesto de tokens; (6)
prompt con contexto; (7) streaming al cliente con eventos §1.2 y buffer de citas hasta
validar IDs; (8) persistencia en `messages` + `message_sources` (con A2.12). Cancelación a
mitad de stream limpia estado y deja el parcial `cancelled`.

### L2.6 — Citas validadas

**Depende de:** L2.5 · **Tests:** U-S2-JL-05.

Cómo debe funcionar: cada marcador de cita del LLM se valida contra BD (el chunk/segmento
existe, es del tenant, versión activa) antes de emitir `citation`; sin offsets fiables →
«segmento N»; el modelo nunca genera la fuente. Cero IDs no autorizados o inventados.

### L2.7 — Evaluación G4

**Depende de:** L2.1–L2.6 · **Tests:** G4 (script reproducible semanal).

Cómo debe funcionar: correr el dataset S1 (≥50 preguntas/idioma, 15 no respondibles);
publicar por idioma: Recall@8 en respondibles, precisión de citas ≥ 0.95, abstención ≥ 0.90
en no respondibles, con numerador/denominador. Nunca maquillar métricas; si faltan clases
reales, transcripciones sintéticas de clase (solo texto) anotadas.

### L2.8 — Medición de latencia

**Depende de:** L2.4 · **Tests:** G4.

p95 de recuperación ≤ 500 ms en corpus de referencia; primer token de chat p95 ≤ 5 s
(requisito §8 del spec). Medidos, no garantizados; publicados con fecha y entorno.

## 3. Tickets API/BD (`A2.x`)

### A2.1 — Migración completa de datos S2

**Depende de:** A1.5 · **Tests:** I-S2-AN-05, I-S2-AN-11.

Entrega una migración ordenada y tenant-aware para `audios`, `ingestion_attempts`,
`variant_confirmation_tokens`, `transcripts`, `segments`, `chunks`, `chunk_segments`,
`embeddings`, `index_generations`, `processing_runs`, `outbox_events`, `conversations`,
`messages` y `message_sources`. `audios` no tiene `storage_key`; intentos registran
consentimiento versionado, lease/fencing, cleanup y estado
`transcript_committed_cleanup_pending`; toda referencia tenant usa FK compuesta. Incluye
índices GIN/HNSW candidatos y los dos índices parciales solo donde el diseño los define.

**Verificación obligatoria:** migrar BD vacía y una versión anterior en compose; inspeccionar
constraints/FKs y ejecutar las suites de dedupe/chat. No se admite una migración de emergencia
en la semana.

### A2.2 — `GET /ingestion/capabilities`

**Depende de:** S1.A8 · **Tests:** U-S2-SG-01.

Cómo debe funcionar: expone los límites **medidos en el spike** (payload máximo, duración,
formatos aceptados, idiomas allowlist, TTLs de intento) — no constantes duras; se actualiza
de la config publicada por el spike. La UI (D2.1) consume esto para el formulario.

### A2.3 — `POST /audios` real

**Depende de:** A2.1, L1.6 · **Tests:** U-S2-AN-01.

Cómo debe funcionar: valida materia tenant, fecha, zona IANA, idioma obligatorio de allowlist,
`privacy_notice_version`, `cloud_processing_accepted=true` y
`third_party_voice_acknowledged=true` antes de reservar. Crea `awaiting_upload` con lease y
URL relativa. **No decide dedupe** porque el hash aún no existe: responde solo `201`, `422`,
`429` o `503`. Tras `duplicate_variant`, acepta un token opaco vigente en un segundo POST y
crea la reserva que exigirá nuevo upload.

### A2.4 — `PUT` binario con streaming

**Depende de:** A2.3 · **Tests:** I-S2-AN-05.

Cómo debe funcionar: recepción streaming sin spool con sesión + CSRF + `attempt_id`; corta
al superar límite. Calcula SHA-256 y limpia antes de responder `200 duplicate_exact` o
`409 duplicate_variant`; solo devuelve `202` al contenido nuevo admitido en el supervisor. El
409 incluye token opaco de un uso/TTL; un segundo PUT verifica hash antes de ASR. Si falla BD
tras recibir, compensa reserva/temporales. Casos `410 upload_expired`, `409 attempt_not_active`
y `422 variant_hash_mismatch` quedan cubiertos.

### A2.5 — Dedupe por identidad exacta

**Depende de:** A2.3 · **Tests:** U-S2-AN-02, I-S2-AN-05.

Cómo debe funcionar: identidad = SHA-256 + idioma + materia + fecha + zona. Se decide en el
PUT tras cleanup: exacto devuelve la clase canónica y libera la reserva; mismo hash con otro
contexto devuelve `409` con `existing_audio_id` y `variant_confirmation_token` hasheado en BD,
de un uso/TTL y ligado a tenant/hash/metadatos. El segundo POST consume el token y el segundo
PUT vuelve a verificar el hash; discrepancia → `rejected`, sin ASR. Una variante confirmada no
muta evidencia/tareas existentes. Se prueban dos uploads simultáneos, token vencido/reutilizado
y tenants distintos.

### A2.6 — Máquina de estados

**Depende de:** A2.1 · **Tests:** U-S2-AN-03.

Cómo debe funcionar: etapas `not_requested|pending|running|succeeded|failed|cancelled`; ASR
incluye `transcript_committed_cleanup_pending` entre commit y `succeeded`. Ese estado no se
expone como éxito y bloquea solo índice/análisis. Agregado: `processing`, `ready`, `partial`,
`failed`; `not_requested` **≠** éxito. Upload expirado, formato rechazado, silencio y pérdida
técnica tienen destinos tipados; toda transición inválida devuelve `409`.

### A2.7 — Cancelación, tombstone y fencing

**Depende de:** A2.6 · **Tests:** U-S2-AN-04, I-S2-AN-06.

Cómo debe funcionar: cancelar invalida el token de fencing → commits tardíos rechazados;
el supervisor cancela subprocess/gRPC y limpia. `DELETE /audios/{id}` = tombstone: cancela
intentos/jobs, borra transcript/chunks/embeddings/tareas derivadas/resumen/citas; eventos
Google ya creados se conservan por defecto (aviso al usuario); eliminarlos exige opción
explícita vía `google_remote_operations`. Borrar mientras corre ASR → cancelación limpia sin
huérfanos. Purga de derivados verificada por tests.

### A2.8 — `retry` vs `reupload`

**Depende de:** A2.6 · **Tests:** I-S2-AN-08.

Cómo debe funcionar: `POST /audios/{id}/retry` exige `{stages:["index"|"analyze"],
transcript_version}` y solo crea runs idempotentes sobre texto. `reupload` solo existe sin
transcript utilizable y crea una nueva sesión efímera con la misma identidad. Matriz de
decisión cubre `409 transcript_unavailable|invalid_transition` y rechaza etapas vacías,
duplicadas, obsoletas o no requeridas.

### A2.9 — Lectura, SSE y exports

**Depende de:** A2.6 · **Tests:** I-S2-AN-07/09.

Cómo debe funcionar: `GET /audios?subject_id=` (listado del tenant), `GET /audios/{id}`
(ficha con estados por etapa + agregado + `attempt`), `GET /audios/{id}/progress` SSE con
**snapshot desde BD al conectar/reconectar** (solo owner), exports: `transcript.txt`
siempre que haya transcript; `transcript.srt` **solo** con tiempos válidos, ordenados y
dentro de la duración (si no: `409 srt_unavailable`). Progreso con bytes reales y
fragmentos `done/total` — cero porcentajes inventados.

### A2.10 — Commit atómico + gate de outbox

**Depende de:** S2.5 (contrato) · **Tests:** I-S2-AN-10.

Cómo debe funcionar: una transacción crea `transcripts`, `segments` y eventos
`index/analyze(enabled=false, blocked_reason=cleanup_pending)`; persiste idioma, modelo,
configuración, versión y precisión. Después pasa a
`transcript_committed_cleanup_pending`; vacío/silencio → `rejected/no_usable_text`. Solo el
reconciliador con cleanup verificado habilita estos eventos. Calendar/notificaciones/borrados
no usan este gate. Prueba roja/verde y recovery post-commit obligatorios.

### A2.11 — `GET /search`

**Depende de:** L2.3 · **Tests:** I-S2-JL-06 (en pareja con L2.4).

Cómo debe funcionar: endpoint del §1.3 con filtros tenant/materia/fechas; snippet + audio +
timestamp válido; `took_ms` real. Comparte el `SearchService` con el chat (una sola
implementación, dos consumidores).

### A2.12 — Persistencia del chat (M7)

**Depende de:** A2.1, L2.5 (contrato) · **Tests:** I-S2-AN-11.

Cómo debe funcionar:

1. Tablas `conversations` (modo `all|subject|class` + `subject_id`/`audio_id` según modo,
   CHECK de coherencia), `messages` (rol, contenido, estado
   `streaming|completed|failed|cancelled`, `client_message_id` único por conversación para
   idempotencia), `message_sources` (todas las fuentes entregadas al modelo, con audio_id,
   segment_id, spans).
2. Endpoints: `POST /chat/conversations` (201/422 chat_mode_invalid),
   `GET /chat/conversations` (lista del tenant), `GET /chat/conversations/{id}/messages`
   (historial paginado), `POST /chat/conversations/{id}/messages` (SSE con fetch;
   `client_message_id` repetido → devuelve el mensaje original sin re-ejecutar), `DELETE
   /chat/conversations/{id}` (204, tombstone y purga de fuentes), `POST
   /chat/conversations/{id}/messages/{message_id}/cancel` (202, parcial `cancelled`).
3. Aislamiento por tenant en todos los endpoints; borrar conversación purga fuentes.

## 4. Tickets Ingesta/ASR (`S2.x`)

### S2.1 — Recepción real y validación

**Depende de:** A2.2/A2.3, S1.A8 · **Tests:** U-S2-SG-02.

Cómo debe funcionar: capabilities servidas con límites del spike; recepción streaming a
`tmpfs` privado por intento con SHA-256 incremental; ffprobe valida contenedor, codecs,
duración real y canales (tabla de decisión del spike; playlists/URLs/malformados
rechazados); el hash y la duración reales los valida ffprobe, no `Content-Length`.

### S2.2 — ffmpeg acotado y fragmentación

**Depende de:** S2.1 · **Tests:** U-S2-SG-03.

Cómo debe funcionar: ffmpeg sin red, argv construido sin interpolación de shell, límites de
CPU/memoria/salida/tiempo; normalización a WAV PCM 16-bit mono al sample rate validado;
fragmentación según los límites **reales** del spike (no asumir 10 min), cortes en
silencios con solapamiento probado.

### S2.3 — Backpressure y reconciliación de fronteras

**Depende de:** S2.2 · **Tests:** U-S2-SG-04.

Cómo debe funcionar: procesamiento secuencial con backpressure (sin decodificar 3 h a RAM);
reconciliación entre fragmentos: eliminar palabras/texto duplicados del overlap, timestamps
globales = offset del fragmento + tiempo local, orden estable. Casos de test: silencios,
fronteras a mitad de palabra, overlap completo.

### S2.4 — Cliente Riva aislado y reintentos clasificados

**Depende de:** S2.2 · **Tests:** U-S2-SG-05.

Cómo debe funcionar: cliente gRPC bloqueante aislado del event loop (executor); deadlines y
cancelación probados; reintentos: gRPC transitorio reintenta (máx 3, backoff+jitter dentro
del lease); auth/idioma/formato inválido **no** reintenta; agotar deadline total →
`requires_reupload`. `P-S2-SG-12` (protegida) regresión mínima contra Riva real tras
cambios de cliente.

### S2.5 — Commit atómico (lado ingesta)

**Depende de:** S2.3/S2.4 · **Tests:** I-S2-SG-06.

Cómo debe funcionar: contrato compartido con A2.10 — transacción única transcript+segmentos
+ outbox deshabilitada; persistencia de idioma/modelo/versión/`timestamp_precision`; vacío o
silencio = resultado sin texto utilizable sin relleno; calidad baja → advertencias
estructuradas (no PII).

### S2.6 — Cleanup en `finally` y gate

**Depende de:** S2.5 · **Tests:** I-S2-SG-07.

Cómo debe funcionar: al terminar ASR (éxito **o** error): cerrar buffers/archivos/clientes,
eliminar original/convertidos/fragmentos; `cleanup_status` verificado de forma
independiente; intento `succeeded` **solo tras commit y cleanup comprobado**; solo entonces
habilita outbox. Test rojo si `succeeded` sin cleanup.

### S2.7 — Reconciliador post-commit y fencing

**Depende de:** S2.6 · **Tests:** I-S2-SG-08/09.

Cómo debe funcionar: proceso muerto tras el commit → el reconciliador verifica cleanup y
habilita outbox **sin retranscribir**; fencing token por intento: propietario vencido no
publica transcript; token obsoleto rechazado.

### S2.8 — Matriz de cancelación

**Depende de:** A2.7 · **Tests:** I-S2-SG-10.

Casos exactos: desconexión durante recepción → cancela+limpia; tras 202 → continúa bajo
lease; cerrar pestaña/SSE tras 202 → **no cancela**; cancelar tras commit → `409` con
estado actual, el transcript no se destruye.

### S2.9 — E2E con clase sintética de 1 h

**Depende de:** S2.1–S2.8, D2.2/D2.3 · **Tests:** E-S2-SG-11.

Cómo debe funcionar: clase sintética de 1 h generada en RAM con texto conocido, transcrita
de punta a punta vía Caddy desde el navegador; evidencia: transcript correcto,
`timestamp_precision` real, límite efectivo publicado, cero persistencia de audio. Demo del
viernes.

## 5. Tickets Infra/Integraciones (`J2.x`)

### J2.1 — Dispatcher de outbox real

**Depende de:** A2.10, U-S1-JF-04 · **Tests:** U-S2-JF-01.

Cómo debe funcionar: consume `outbox_events` y publica solo IDs/config no sensible. Rechaza
`index/analyze` bloqueados por `cleanup_pending`; Calendar, notificaciones y borrados ya
habilitados se despachan tras revalidar autorización/tombstone/versión. Backoff+jitter máx. 3
solo para transitorios; no transitorios no reintentan.

### J2.2 — Job `index(audio_id)` idempotente

**Depende de:** J2.1 · **Tests:** I-S2-JF-02.

Cómo debe funcionar: encapsula la lógica de L2.2 (día 4–5 se conecta al real; antes stub que
registra la llamada); verifica propiedad/tombstone/versión antes de publicar; doble entrega
→ un solo índice; sin versiones parciales activas; reintentos backoff+jitter (máx 3
transitorios).

### J2.3 — Reconstrucción tras perder Redis

**Depende de:** J2.1 · **Tests:** I-S2-JF-03.

Cómo debe funcionar: `FLUSHALL` en entorno de prueba → los jobs se regeneran desde
BD/outbox y recorren el camino completo hasta completarse; **no** se reconstruye audio
(jamás).

### J2.4 — Reconciliador

**Depende de:** J2.2 · **Tests:** I-S2-JF-04.

Cómo debe funcionar: intentos muertos marcados; outbox atascada re-publicada; ejecuciones
duplicadas resueltas por unicidad/lease. Fault injection con J2.7.

### J2.5 — Observabilidad mínima

**Depende de:** J2.1 · **Tests:** C-S2-JF-10 (checklist operativa).

Logs JSON con `request_id/audio_id/attempt_id/run_id` sin payloads sensibles; métricas:
RAM/tmpfs/slots, lag de outbox, retries, edad de temporales; **alerta inmediata por cleanup
fallido**; panel mínimo de fallos por etapa.

**Verificación obligatoria:** inyectar cleanup fallido en compose y adjuntar captura redactada
de alerta, métricas y ausencia de payload sensible a la evidencia C-S2-JF-10.

### J2.6 — Smoke E2E automatizado

**Depende de:** J2.2, S2.9, D2.2, D2.6 · **Tests:** E-S2-JF-06.

Smoke en cada MR: upload → transcript → cleanup → índice → pregunta con cita, contra
compose. Fixtures conforme a las reglas de PLAN_TESTS §0.4 (audio sintético en RAM).

### J2.7 — Fault injection coordinado

**Depende de:** S2.5, A2.10 · **Tests:** I-S2-JF-05.

Crash inyectado antes y después del commit con áreas API/BD e Ingesta; resultado según contrato:
crash pre-commit → nada publicado, audio limpiado; crash post-commit → reconciliador
habilita outbox sin retranscribir. Lease vencido no marca cleanup verificado. Evidencia
documentada en bitácoras.

## 6. Tickets Web/UX (`D2.x`)

### D2.1 — Formulario de upload (M2)

### D2.2 — Upload streaming

**Depende de:** A2.4 · **Tests:** U-S2-DA-02.

Cómo debe funcionar: `PUT` a la URL relativa con `fetch` streaming; progreso real de bytes
desde el stream; cancelar la subida **cancela el intento** (llamada a la API de cancelación
+ liberación de `File`/object URLs); sin Server Actions para el binario.

### D2.3 — Progreso honesto

**Depende de:** A2.9 · **Tests:** U-S2-DA-03.

Cómo debe funcionar: SSE con `EventSource` (GET) + polling como fallback activable; bytes
recibidos y fragmentos completados/total; **cero porcentajes inventados**; snapshot al
reconectar. Estados visibles incluyen `transcript_committed_cleanup_pending` como cleanup
pendiente, nunca como éxito.

### D2.4 — Biblioteca

**Depende de:** A2.9 · **Tests:** E-S2-DA-06.

Cómo debe funcionar: listado por materia con estado agregado **y** estados por etapa;
aviso permanente «audio no conservado»; botones diferenciados «volver a subir» (sin
transcript) ≠ «reintentar análisis/índice» (con transcript); el estado `partial` distingue
qué etapa falló.

### D2.5 — `TranscriptReader`

**Depende de:** A2.9 · **Tests:** C-S2-DA-04.

Cómo debe funcionar: segmentos enlazables/resaltables (`?segment=`); timestamps visibles
**solo si son válidos** (`timestamp_precision != none`), si no «segmento N»; export
TXT/SRT condicionado según el contrato (SRT 409 → botón deshabilitado con explicación);
resumen vacío si `not_requested`.

### D2.6 — Chat UI

**Depende de:** L2.5, A2.12 · **Tests:** C-S2-DA-05.

Cómo debe funcionar: `/chat` con historial; composer con modo validado; SSE con **`fetch`**
(no EventSource — POST); render `snapshot/delta/citation/done/error`; botón cancelar;
estados por mensaje y paginación. Si el stream se corta, consulta el mensaje persistido en vez
de reenviar el mismo `client_message_id`; solo `done|error` es terminal.

### D2.7 — Citas clicables

**Depende de:** L2.6, D2.5 · **Tests:** C-S2-DA-05.

Cómo debe funcionar: cita `[Materia · Clase · mm:ss]` → `/biblioteca/{audio_id}?segment=…`
con texto resaltado; sin tiempos → «segmento N»; el Markdown renderizado se **sanitiza**;
cero enlaces arbitrarios del modelo (solo los del evento `citation`).

### D2.8 — Privacidad en el navegador (acotado a S2)

**Depende de:** — · **Tests:** C-S2-DA-07.

`no-store` en todas las rutas privadas; liberar `File`/object URLs al terminar/cancelar;
sin IndexedDB ni Cache Storage para datos privados; barrido global: ningún reproductor ni
botón de descarga de audio en toda la app.

## 7. Flujo integrado de la semana (corte vertical)

1. **Upload:** formulario D2.1 → `POST /audios` reserva (A2.3) → `PUT` streaming
   (D2.2/A2.4) → `202`, `200 duplicate_exact` o `409 duplicate_variant`; este último limpia,
   entrega token y exige segundo POST+PUT.
2. **Transcripción:** supervisor S2 (S2.1–S2.4) → commit atómico (S2.5+A2.10) → cleanup
   verificado (S2.6) → reconciliador habilita outbox (S2.7).
3. **Indexación:** dispatcher (J2.1) → `index(audio_id)` (J2.2/L2.2) → índice híbrido
   activo.
4. **Consulta:** `/search` (L2.4+A2.11) y chat con citas (L2.5/L2.6 + A2.12) → UI D2.5–D2.7.
5. **Evidencia:** E2E clase de 1 h (S2.9) + smoke CI (J2.6) + fault injection (J2.7).
