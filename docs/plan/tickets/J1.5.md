## 1. Ticket summary

- **Objective:** leave the `worker` and `scheduler` ARQ connected to Redis, a basic
  outbox dispatcher that applies the cleanup gate only to
  `index.requested`/`analyze.requested`, and per-process `/healthz`/`/readyz`.
- **Scope:** `WorkerSettings` for worker and scheduler, the outbox service and publication
  policy, a health script for processes without HTTP, and the real API `/readyz`.
- **Out of scope:** real index/analysis jobs (S2/J2.1), retries with backoff (J2.x),
  reconstruction after losing Redis (J2.3), reminder cron scheduler (J4.2), full
  observability (J2.5).
- **Typed dependency:** `code` J1.1 (compose and Redis); `contract` §1.3 (`outbox_events`
  shape); `code` A1.8 (endpoints) and the `outbox_events` table + async engine (A1.5/A1.7).
  If the table or the engine does not exist, **do not invent schema**: coordinate with
  owner A.
- **Deliverables:** `apps/api/app/workers/arq_app.py`,
  `apps/api/app/workers/scheduler.py` (or `arq_app.py` with two settings),
  `apps/api/app/services/outbox.py`,
  `apps/api/app/workers/dispatcher.py`, a real `/readyz` in the API,
  `apps/api/tests/unit/test_outbox_policy.py`.
- **Acceptance criteria:**
  - [ ] `worker` and `scheduler` start against Redis and their compose healthcheck is healthy.
  - [ ] API `/readyz` returns 200 only with Postgres **and** Redis available; 503 if
    either fails; it **never** calls paid providers.
  - [ ] U-S1-JF-04 green: the gate blocks `index.requested`/`analyze.requested` until
    `cleanup_status=verified`, and does not block Calendar/notifications/deletions.
  - [ ] The dispatcher publishes only IDs/non-sensitive configuration.
- **Tests/evidence:** **U-S1-JF-04** and the `/healthz`/`/readyz` part of **I-S1-JF-01**.
- **Planned files:** those in §Deliverables; the `outbox_events` model/migration belongs
  to A (declare the dependency when claiming).

## 2. Delivery design

### 2.1 Worker and scheduler

```python
# apps/api/app/workers/arq_app.py
from arq import cron
from arq.connections import RedisSettings

async def index(ctx, audio_id: str, transcript_version: int) -> None:
    # S1: stub that only logs IDs; S2/J2.1 connects the real index.
    ctx["logger"].info("index.noop", audio_id=audio_id, transcript_version=transcript_version)

async def analyze(ctx, audio_id: str) -> None:
    ctx["logger"].info("analyze.noop", audio_id=audio_id)

class WorkerSettings:
    functions = [index, analyze]
    redis_settings = RedisSettings.from_dsn(str(settings.redis_url))
    health_check_interval = 30
    health_check_key = "arq:health-check:worker"
    keep_result = 60
    max_tries = 1          # S1: no retries; J2.x defines backoff/jitter
```

- `scheduler.py` defines `SchedulerSettings` with `cron_jobs = [cron(dispatch_outbox, second=…)…]`
  approximately every minute (ARQ cron is per minute; document the granularity) and its own
  `health_check_key = "arq:health-check:scheduler"`.
- In S1 there are no real jobs: the stubs are only invoked from the dispatcher.
- JSON logs with IDs, no payloads (observability rule of the spec).

### 2.2 Health of processes without HTTP (decided 2026-09-27, implemented)

`worker` and `scheduler` do not expose HTTP. "Per-process `/healthz`" is satisfied with a
process healthcheck in compose, without a custom script: `arq app.workers.arq_app.<Settings>
--check`, which exits 0 only if the `<queue>:health-check` key exists in Redis.

- Separate queues (`arq:queue` worker, `arq:scheduler` scheduler), so each process has
  its own key and the scheduler does not run the worker's jobs.
- `health_check_interval = 30` (ARQ uses 3600 by default): the key expires ~31 s after
  the process dies or Redis is lost.
- Verified in compose: both `healthy`; with the worker stopped for 33 s, `--check`
  exits 1.
- Test: `apps/api/tests/unit/test_arq_settings.py`.

### 2.3 API `/readyz`

- Replace the placeholder in `apps/api/app/main.py`.
- `SELECT 1` against Postgres (shared async engine) and `PING` to Redis; both with short
  timeout; 200 `{"status":"ready"}` or 503 `{"status":"not_ready","detail":[...]}` redacted.
- **Never** invoke Riva/LLM/Google from a healthcheck.
- If `pgvector` is not migrated yet (A1.7/S2), do not require the extension in S1.

### 2.4 Outbox and cleanup gate

Frozen shape (§1.3): `id`, `tenant (user_id)`, `type`, `resource_id`,
`resource_version`, `enabled`, `blocked_reason`, `attempts`, `published_at`.

Initial catalog: `index.requested`, `analyze.requested`, `calendar.event.sync`,
`notification.schedule`.

Policy (pure function in `services/outbox.py`, testable without the DB):

| Type | Rule |
|---|---|
| `index.requested` / `analyze.requested` from ingestion | publishable **only** if `cleanup_status == "verified"`; otherwise it stays `blocked_reason=cleanup_pending` and is not published |
| `calendar.event.sync`, `notification.schedule`, deletions | publishable if `enabled=true`; born enabled in their own transaction after validating authorization, tombstone and version; **do not** depend on cleanup |
| unknown | **fail closed**: not publishable + log/metric |

The dispatcher (`workers/dispatcher.py`) in S1:

1. Selects events with `published_at IS NULL`, `enabled=true`, in a transaction with
   `FOR UPDATE SKIP LOCKED`.
2. Applies the policy; if blocked, it updates `blocked_reason` and does not publish.
3. Enqueues the ARQ job with **only IDs** and safe configuration, and marks `published_at`.
4. Does not retry or increment `attempts` in S1 (J2.1 completes it).

> The cleanup gate "only applies to ingestion-derived index/analyze": the derived/not
> derived distinction is resolved by the event origin; document it in the function and
> cover it with U-S1-JF-04.

## 3. Step by step

1. Claim in `CLAIMS.md` and branch `s1/j1.5-arq-outbox`.
2. Confirm with the A owner: `outbox_events` table, async engine (`app/core/db.py`) and
   `cleanup_status` available. Record the agreement in the PR.
3. Write the pure policy and its test **first**:
   ```bash
   cd apps/api && uv run pytest tests/unit/test_outbox_policy.py -q
   ```
4. Implement `arq_app.py` (worker and scheduler) and `arq ... --check` healthchecks (done).
5. Implement the dispatcher with `FOR UPDATE SKIP LOCKED` and IDs-only publication.
6. Replace the `/readyz` placeholder with the real checks.
7. Update `infra/docker-compose.yml` (coordinated with J1.1): `worker`/`scheduler`
   commands and `python -m app.workers.health --role …` healthchecks.
8. Bring up and verify:
   ```bash
   cd infra && docker compose up -d --build --wait
   docker compose ps
   curl -k -o /dev/null -w '%{http_code}\n' https://localhost/readyz    # expected 200
   docker compose stop redis && curl -k -o /dev/null -w '%{http_code}\n' https://localhost/readyz  # expected 503
   ```
9. Record evidence, update the logbook and open the PR.

## 5. Coordination and risks

- **Without the outbox table there is no dispatcher:** it is a blocking dependency of
  A1.5/A1.7/A1.8; do not create a parallel migration without agreement (crosses areas).
- **ARQ and compatibility:** pin the `arq` version with the lockfile; the cron scheduler
  has minute granularity (J4.2 will refine it).
- **Worker healthcheck:** if the team demands literal HTTP, resolve it in S1 before
  closure (open question from §2.2).
- **Redis down:** `/readyz` must fail without taking `/healthz` down (liveness ≠ readiness).
