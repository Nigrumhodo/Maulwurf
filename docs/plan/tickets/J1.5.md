## 1. Ficha del ticket

- **Objetivo:** dejar `worker` y `scheduler` ARQ conectados a Redis, un dispatcher básico de
  outbox que aplique el gate de cleanup solo a `index.requested`/`analyze.requested`, y
  `/healthz`/`/readyz` por proceso.
- **Alcance:** `WorkerSettings` de worker y scheduler, servicio de outbox y política de
  publicación, script de salud para procesos sin HTTP, `/readyz` real de API.
- **No alcance:** jobs reales de índice/análisis (S2/J2.1), reintentos con backoff (J2.x),
  reconstrucción tras perder Redis (J2.3), scheduler cron de recordatorios (J4.2),
  observabilidad completa (J2.5).
- **Dependencia tipada:** `código` J1.1 (compose y Redis); `contrato` §1.3 (shape
  `outbox_events`); `código` A1.8 (endpoints) y tabla `outbox_events` + engine async (A1.5/A1.7).
  Si la tabla o el engine no existen, **no inventar esquema**: coordinarlo con el owner A.
- **Entregables:** `apps/api/app/workers/arq_app.py`,
  `apps/api/app/workers/scheduler.py` (o `arq_app.py` con dos settings),
  `apps/api/app/workers/health.py`, `apps/api/app/services/outbox.py`,
  `apps/api/app/workers/dispatcher.py`, `/readyz` real en la API,
  `apps/api/tests/unit/test_outbox_policy.py`.
- **Criterios de aceptación:**
  - [ ] `worker` y `scheduler` arrancan contra Redis y su healthcheck de compose queda sano.
  - [ ] `/readyz` de API devuelve 200 solo con Postgres **y** Redis disponibles; 503 si alguno
    falla; **no** llama a proveedores pagados.
  - [ ] U-S1-JF-04 en verde: el gate bloquea `index.requested`/`analyze.requested` hasta
    `cleanup_status=verified`, y no bloquea Calendar/notificaciones/borrados.
  - [ ] El dispatcher publica solo IDs/configuración no sensible.
- **Pruebas/evidencia:** **U-S1-JF-04** y la parte de `/healthz`/`/readyz` de **I-S1-JF-01**.
- **Archivos previstos:** los de §Entregables; el modelo/migración de `outbox_events` es de
  A (declarar la dependencia al reclamar).

## 2. Diseño de la entrega

### 2.1 Worker y scheduler

```python
# apps/api/app/workers/arq_app.py
from arq import cron
from arq.connections import RedisSettings

async def index(ctx, audio_id: str, transcript_version: int) -> None:
    # S1: stub que solo registra IDs; S2/J2.1 conecta el índice real.
    ctx["logger"].info("index.noop", audio_id=audio_id, transcript_version=transcript_version)

async def analyze(ctx, audio_id: str) -> None:
    ctx["logger"].info("analyze.noop", audio_id=audio_id)

class WorkerSettings:
    functions = [index, analyze]
    redis_settings = RedisSettings.from_dsn(str(settings.redis_url))
    health_check_interval = 30
    health_check_key = "arq:health-check:worker"
    keep_result = 60
    max_tries = 1          # S1: sin reintentos; J2.x define backoff/jitter
```

- `scheduler.py` define `SchedulerSettings` con `cron_jobs = [cron(dispatch_outbox, second=…)…]`
  aproximado a cada minuto (ARQ cron es por minuto; documentar la granularidad) y su propia
  `health_check_key = "arq:health-check:scheduler"`.
- En S1 no hay jobs reales: los stubs solo se invocan desde el dispatcher.
- Logs JSON con IDs, sin payloads (regla de observabilidad de la spec).

### 2.2 Salud de procesos sin HTTP

`worker` y `scheduler` no exponen HTTP. Se usa un comando de salud en el healthcheck de
compose:

```bash
python -m app.workers.health --role worker
```

Criterios del script (exit 0/1):

1. `PING` a Redis correcto.
2. La clave `arq:health-check:<role>` existe y su TTL es positivo.
3. Sin excepciones de conexión en el último intervalo (best-effort por TTL de la clave).

> Punto abierto: la spec dice «`/healthz` por proceso». Para worker/scheduler se interpreta
> como healthcheck de proceso (no HTTP) y se registrará así en la evidencia; si el equipo
> quiere HTTP literal, habría que añadir un sidecar o un endpoint en un proceso aparte (no
> recomendado).

### 2.3 `/readyz` de la API

- Sustituir el placeholder de `apps/api/app/main.py`.
- `SELECT 1` contra Postgres (engine async compartido) y `PING` a Redis; ambos con timeout
  corto; 200 `{"status":"ready"}` o 503 `{"status":"not_ready","detail":[...]}` redactado.
- **Nunca** invocar Riva/LLM/Google desde un healthcheck.
- Si `pgvector` aún no está migrado (A1.7/S2), no exigir la extensión en S1.

### 2.4 Outbox y gate de cleanup

Shape congelado (§1.3): `id`, `tenant (user_id)`, `type`, `resource_id`,
`resource_version`, `enabled`, `blocked_reason`, `attempts`, `published_at`.

Catálogo inicial: `index.requested`, `analyze.requested`, `calendar.event.sync`,
`notification.schedule`.

Política (función pura en `services/outbox.py`, testeable sin BD):

| Tipo | Regla |
|---|---|
| `index.requested` / `analyze.requested` de ingesta | publicable **solo** si `cleanup_status == "verified"`; si no, queda `blocked_reason=cleanup_pending` y no se publica |
| `calendar.event.sync`, `notification.schedule`, borrados | publicables si `enabled=true`; nacen habilitados en su propia transacción tras validar autorización, tombstone y versión; **no** dependen del cleanup |
| desconocido | **fail closed**: no publicable + log/métrica |

El dispatcher (`workers/dispatcher.py`) en S1:

1. Selecciona eventos con `published_at IS NULL`, `enabled=true`, en transacción con
   `FOR UPDATE SKIP LOCKED`.
2. Aplica la política; si está bloqueado, actualiza `blocked_reason` y no publica.
3. Encola el job ARQ con **solo IDs** y configuración segura, y marca `published_at`.
4. No reintenta ni incrementa `attempts` en S1 (J2.1 lo completa).

> El gate de cleanup «solo aplica a index/analyze derivados de ingesta»: la distinción
> derivado/no derivado se resuelve por el origen del evento; dejarlo documentado en la
> función y cubierto por U-S1-JF-04.

## 5. Coordinaciones y riesgos

- **Sin la tabla outbox no hay dispatcher:** es dependencia bloqueante de A1.5/A1.7/A1.8; no
  crear una migración paralela sin acuerdo (cruza áreas).
- **ARQ y compatibilidad:** fijar la versión de `arq` con el lockfile; el scheduler cron tiene
  granularidad de minuto (J4.2 afinará).
- **Healthcheck de worker:** si el equipo exige HTTP literal, resolverlo en S1 antes del
  cierre (pregunta abierta de §2.2).
- **Redis caído:** `/readyz` debe fallar sin tumbar `/healthz` (liveness ≠ readiness).
