## 1. Scope delivered

| In this slice | Not in this slice |
|---|---|
| `GET /tasks` with status/subject/due filters and keyset cursor | `POST /tasks` |
| `GET /tasks/{id}` | `PATCH /tasks/{id}` optimistic-locking writes |
| Tenant isolation and 404 for foreign tasks | `confirm`, `dismiss`, `complete` |
| `TaskOut` with sources, reconstructed evidence, pending revision | A3.2 `task_evidence` table |
| Caddy `/tasks` route | A3.4 atomic confirmation and outbox |
| PATCH active edits and confirmed-task revisions | `POST /tasks` |

Evidence is reconstructed from the existing `task_sources` provenance and the immutable
`segments.text` slice. It is not yet a separate persisted `task_evidence` row (A3.2), so the
quote remains exact but depends on the source span staying reconstructible.

## 2. PATCH contract

`PATCH /tasks/{id}` accepts `version` plus partial content, due or `event_block` fields.
It locks the task row, validates the final state and applies the A3.1 constraints.

- Stale version -> `409 version_conflict` (`current_version`, `current_status`).
- `dismissed`/`completed` -> `409 invalid_transition`.
- `needs_review`/`pending` -> active update, `version += 1`; due changes also bump
  `due_version`.
- `confirmed` -> new `task_revisions` row (`edit_of_confirmed`, `base_task_version`,
  `pending_confirmation`, `proposed_fields`); active fields and `version` stay put.
- `event_block` is replaced when present: all-day pair or timed pair, end strictly later,
  never mixed.
- `pending_revision.proposed_fields` is returned by the read shape.

## 4. Rules

- `status` is validated against the A3.1 closed vocabulary; invalid values are 422.
- A foreign `subject_id` yields an empty page, never a 404 (no tenant disclosure).
- `limit` is 1..200; the cursor is opaque and keyset over `(created_at, id)`.
- The API never accepts a quote, timestamp, task status or class id from the caller.
- Evidence is reconstructed from the source span and `segments.text`; malformed spans are
  omitted rather than invented.
- `status` and `calendar_sync_status` remain separate; `pending_revision` is separate.
- `Cache-Control: no-store` is applied by the global API middleware.
