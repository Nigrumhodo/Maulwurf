## 1. Ficha del ticket

- **Objetivo:** pipeline de GitHub Actions que ejecute lint, tipos, unitarias, integración con
  Postgres/pgvector/Redis reales, Vitest y builds de `api`/`ingest`/`web`, sin secretos de
  proveedores en los MR, **más** `.github/pull_request_template.md` que implementa el formato
  de PR de ADR-0004 (alcance ampliado por decisión del 2026-09-25).
- **Alcance:** workflow de calidad, servicios de CI para la capa de integración, scripts de
  lint/tipos/tests que falten en los manifests, y la plantilla de PR.
- **No alcance:** CD/despliegue (J4.7), pruebas `P-` (siguen protegidas y manuales/programadas),
  E2E de navegador (aparecen en S2), branch protection (configuración de administración, se
  documenta y evidencia), cambios a las reglas de ADR-0004 (solo las materializa).
- **Dependencia tipada:** `código` J1.1 (Dockerfiles y compose). `contrato` ADR-0002
  ([../../adr/ADR-0002-versiones.md](../../adr/ADR-0002-versiones.md)) deja runner/registry e
  imagen exactos a este ticket; ADR-0004
  ([../../adr/ADR-0004-commits-pr.md](../../adr/ADR-0004-commits-pr.md)) fija el formato de
  commit/PR. `código` A1.7 si se quiere ejecutar
  migraciones en CI (condicional).
- **Entregables:** `.github/workflows/quality.yml`;
  `.github/pull_request_template.md` (ADR-0004); scripts faltantes en `apps/web/package.json`
  (`typecheck`, `test`); checklist de gates manuales (branch protection); enlace al run verde.
- **Criterios de aceptación:**
  - [ ] El pipeline corre en cada PR y en `develop`, con permisos mínimos y sin secretos.
  - [ ] Las suites `P-`/`load` **no** se ejecutan en MR; los tests de proveedor no se seleccionan
    por defecto.
  - [ ] La capa de integración usa Postgres `pgvector/pgvector:pg16` y Redis reales.
  - [ ] Los tres builds de imagen pasan.
  - [ ] `.github/pull_request_template.md` existe y cubre resumen, ticket/claim, test plan,
    evidencia y checklist de ADR-0004.
  - [ ] El PR del ticket muestra el pipeline verde enlazado como evidencia.
- **Pruebas/evidencia:** «pipeline verde en MR» (criterio del ticket) y, cuando existan,
  I-S1-AN-04 y las suites `I-S1-*` que el pipeline ejecute.
- **Archivos previstos:** `.github/workflows/quality.yml`, `.github/pull_request_template.md`,
  `apps/web/package.json`, `scripts/ci/` si hace falta un guard de secretos.

## 2. Diseño de la entrega

### 2.1 Jobs

```yaml
name: quality
on:
  pull_request:
  push:
    branches: [develop]
permissions:
  contents: read
concurrency:
  group: quality-${{ github.ref }}
  cancel-in-progress: true
```

| Job | Qué corre | Notas |
|---|---|---|
| `python-static` | matriz `[api, ingest]`: `ruff check .`, `mypy .` | `uv sync --frozen --extra dev` |
| `python-unit` | matriz `[api, ingest]`: `pytest -m "not integration and not provider and not load"` | sin servicios |
| `web` | `npm ci`, `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build` | Vitest con `--passWithNoTests` hasta que existan suites (TODO quitar) |
| `integration` | Postgres + Redis de servicio, `pytest -m "integration"` en api e ingest | `P-`/`load` excluidos |
| `build-images` | `docker build` de `apps/api`, `apps/ingest`, `apps/web` | buildx con caché de Actions |

Reglas:

1. **Cero secretos de proveedores.** No se referencian `secrets.NVIDIA_API_KEY`,
   `GOOGLE_*` ni equivalentes. El workflow de Hoplite sigue aparte.
2. **Exclusión explícita de `P-`:** cada invocación de pytest usa
   `-m "not provider and not load"`; prohibido un `pytest` sin marcador.
3. **Postgres de CI** fijado por digest (mismo que compose) con `health-cmd: pg_isready`;
   Redis con healthcheck. `MAULWURF_DATABASE_URL`/`MAULWURF_REDIS_URL` apuntan a `localhost`.
4. **Migraciones:** si A1.7 ya entregó `alembic.ini`, el job de integración ejecuta
   `uv run alembic upgrade head` antes de los tests (refuerza I-S1-AN-04).
5. **Builds sin push en MR**; el push a registry es S4/J4.7, no este ticket.
6. **Permisos mínimos** (`contents: read`) y sin `pull_request_target`.

### 2.2 Ajustes en `apps/web/package.json`

Agregar scripts para que CI no dependa de comandos ad-hoc:

```json
"typecheck": "tsc --noEmit",
"test": "vitest run --passWithNoTests"
```

`--passWithNoTests` es temporal mientras el directorio esté vacío; el ticket de pruebas de D
lo retira. Requiere review de quien tenga claim activo en `apps/web` o del líder.

### 2.3 Plantilla de PR (alcance ampliado)

`.github/pull_request_template.md` materializa ADR-0004: resumen 1–3 puntos, ticket/claim,
test plan/verificación, evidencia y checklist (1 review, CI verde, sin secretos/`.env`/audio,
spec/plan actualizados si cambia contrato, fila de `CLAIMS.md`). Ya existe un borrador en el
árbol de trabajo; el owner de J1.4 lo revisa, lo ajusta a ADR-0004 y lo incluye en el PR.
No cambia las reglas del ADR: solo las hace operativas en GitHub.

### 2.4 Gate manual (no versionable)

- Branch protection de `develop`: PR obligatorio, 1 review, checks de `quality` requeridos.
- Se documenta en el PR y se evidencia con captura redactada del ajuste; si no hay permisos de
  administración, queda como pendiente explícito, no como hecho.

## 5. Coordinaciones y riesgos

- **Suites vacías:** pytest retorna código 5 sin tests; usar el wrapper acordado
  (`code=$?; [ $code -eq 0 ] || [ $code -eq 5 ]`) solo mientras no existan suites, con
  `> TODO:` visible en el workflow, y retirarlo antes del cierre de S1.
- **`tsc`/Vitest no estaban configurados:** el ajuste de scripts cruza a `apps/web`.
- **Duración/caché:** cachear `uv` y `npm`; el build de Next es el paso más lento.
- **Secretos accidentales:** añadir un guard que falle si el diff agrega patrones de claves
  (p. ej. `scripts/ci/check_no_secrets.sh`), sin imprimir valores.
- **Límites de concurrencia:** `cancel-in-progress` evita runs duplicados en pushes seguidos.
