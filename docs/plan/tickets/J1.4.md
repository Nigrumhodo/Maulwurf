## 1. Ticket summary

- **Objective:** a GitHub Actions pipeline that runs lint, types, unit tests, integration
  with real Postgres/pgvector/Redis, Vitest and builds of `api`/`ingest`/`web`, without
  provider secrets in MRs, **plus** a `.github/pull_request_template.md` that implements
  the ADR-0004 PR format (scope extended by the 2026-09-25 decision).
- **Scope:** quality workflow, CI services for the integration layer, missing
  lint/types/test scripts in the manifests, and the PR template.
- **Out of scope:** CD/deployment (J4.7), `P-` tests (remain protected and
  manual/scheduled), browser E2E (appear in S2), branch protection (admin configuration,
  documented and evidenced), changes to the ADR-0004 rules (it only materializes them).
- **Typed dependency:** `code` J1.1 (Dockerfiles and compose). `contract` ADR-0002
  ([../../adr/ADR-0002-versiones.md](../../adr/ADR-0002-versiones.md)) leaves the exact
  runner/registry and image to this ticket; ADR-0004
  ([../../adr/ADR-0004-commits-pr.md](../../adr/ADR-0004-commits-pr.md)) fixes the
  commit/PR format. `code` A1.7 if migrations are to be run in CI (conditional).
- **Deliverables:** `.github/workflows/quality.yml`;
  `.github/pull_request_template.md` (ADR-0004); missing scripts in
  `apps/web/package.json` (`typecheck`, `test`); manual gates checklist (branch
  protection); link to the green run.
- **Acceptance criteria:**
  - [ ] The pipeline runs on every PR and on `develop`, with least privileges and no
    secrets.
  - [ ] The `P-`/`load` suites are **not** run in MRs; provider tests are not selected
    by default.
  - [ ] The integration layer uses real Postgres `pgvector/pgvector:pg16` and Redis.
  - [ ] The three image builds pass.
  - [ ] `.github/pull_request_template.md` exists and covers summary, ticket/claim, test
    plan, evidence and the ADR-0004 checklist.
  - [ ] The ticket PR shows the green pipeline linked as evidence.
- **Tests/evidence:** "green pipeline in MR" (ticket criterion) and, when they exist,
  I-S1-AN-04 and the `I-S1-*` suites the pipeline runs.
- **Planned files:** `.github/workflows/quality.yml`, `.github/pull_request_template.md`,
  `apps/web/package.json`, `scripts/ci/` if a secrets guard is needed.

## 2. Delivery design

### 2.1 Jobs

```yaml
name: quality
on:
  pull_request:
  push:
    branches: [develop]
permissions:
  contents: read
concurrency:
  group: quality-${{ github.ref }}
  cancel-in-progress: true
```

| Job | What it runs | Notes |
|---|---|---|
| `python-static` | matrix `[api, ingest]`: `ruff check .`, `mypy .` | `uv sync --frozen --extra dev` |
| `python-unit` | matrix `[api, ingest]`: `pytest -m "not integration and not provider and not load"` | no services |
| `web` | `npm ci`, `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build` | Vitest with unit suites (U-S1-DA-01/02, C-S1-DA-03) |
| `integration` | service Postgres + Redis, `pytest -m "integration"` in api and ingest | `P-`/`load` excluded |
| `build-images` | `docker build` of `apps/api`, `apps/ingest`, `apps/web` | buildx with Actions cache |

Rules:

1. **Zero provider secrets.** `secrets.NVIDIA_API_KEY`, `GOOGLE_*` or equivalents are
   not referenced. The Hoplite workflow remains separate.
2. **Explicit `P-` exclusion:** every pytest invocation uses
   `-m "not provider and not load"`; a bare `pytest` is forbidden.
3. **CI Postgres** pinned by digest (same as compose) with `health-cmd: pg_isready`;
   Redis with a healthcheck. `MAULWURF_DATABASE_URL`/`MAULWURF_REDIS_URL` point to
   `localhost`.
4. **Migrations:** if A1.7 has already delivered `alembic.ini`, the integration job runs
   `uv run alembic upgrade head` before the tests (reinforces I-S1-AN-04).
5. **Builds without push in MRs**; the registry push is S4/J4.7, not this ticket.
6. **Least privileges** (`contents: read`) and no `pull_request_target`.

### 2.2 Adjustments in `apps/web/package.json`

Add scripts so CI does not depend on ad-hoc commands:

```json
"typecheck": "tsc --noEmit",
"test": "vitest run"
```

`--passWithNoTests` was temporary while the directory was empty; it was removed in D1.4/D1.5
when the first Web unit suites landed. Requires review from whoever has an active claim on
`apps/web` or from the lead.

### 2.3 PR template (extended scope)

`.github/pull_request_template.md` materializes ADR-0004: 1–3 point summary,
ticket/claim, test plan/verification, evidence and checklist (1 review, green CI, no
secrets/`.env`/audio, spec/plan updated if the contract changes, `CLAIMS.md` row). A
draft already exists in the working tree; the J1.4 owner reviews it, aligns it with
ADR-0004 and includes it in the PR. It does not change the ADR rules: it only makes them
operational in GitHub.

### 2.4 Manual gate (not versionable)

- Branch protection of `develop`: required PR, 1 review, required `quality` checks.
- It is documented in the PR and evidenced with a redacted screenshot of the setting; if
  there are no admin permissions, it remains an explicit pending item, not a done one.

## 3. Step by step

1. Claim in `CLAIMS.md` and branch `s1/j1.4-ci-calidad`.
2. Confirm that J1.1 delivered the Dockerfiles and compose; note the pgvector digest for
   CI.
3. Write `.github/workflows/quality.yml` with the five jobs and the §2.1 rules.
4. Review and close `.github/pull_request_template.md` per ADR-0004 (§2.3).
5. Add the `apps/web/package.json` scripts (§2.2).
6. Validate locally whatever is possible:
   ```bash
   cd apps/api && uv sync --frozen --extra dev && uv run ruff check . && uv run mypy .
   cd apps/ingest && uv sync --frozen --extra dev && uv run ruff check . && uv run mypy .
   cd apps/web && npm ci && npm run lint && npm run typecheck && npm run test && npm run build
   ```
7. Document branch protection (applied or pending) in the PR body.
8. Open the PR; iterate until the pipeline is green. Link the PR run as
   evidence (public repo URL, without logs containing sensitive data).

## 5. Coordination and risks

- **Empty suites:** pytest returns code 5 without tests; use the agreed wrapper
  (`code=$?; [ $code -eq 0 ] || [ $code -eq 5 ]`) only while suites do not exist, with a
  visible `> TODO:` in the workflow, and remove it before S1 closes.
- **`tsc`/Vitest were not configured:** the script change crosses into `apps/web`.
- **Duration/cache:** cache `uv` and `npm`; the web build is the slowest step.
- **Accidental secrets:** add a guard that fails if the diff adds key patterns (landed as
  `scripts/ci/check_no_secrets.sh` with J2.9), without printing values.
- **Concurrency limits:** `cancel-in-progress` avoids duplicate runs on consecutive
  pushes.
