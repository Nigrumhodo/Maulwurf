## 2. Contract additions

The browser starts the consent flow through two additive routes:

```text
GET /integrations/google/connect
GET /integrations/google/reconnect
```

They delegate to the same `_start_calendar_flow` as the `POST` routes: same signed `state`
bound to `session.user_id`, same rate limit, same `302` to Google and `mw_oauth` cookie.
The difference is the entry point: a `fetch` `POST` cannot follow the cross-origin `302` to
Google nor render the consent screen, so the UI uses a real anchor. Expected start failures
redirect to `/settings?calendar=error&reason=...` instead of rendering JSON in a navigation.
The `POST` routes remain for API clients.

No task field changed: `calendar_sync_status`, `calendar_id` and `calendar_event_id` already
come from J3.4/D3.6.

## 3. Behavior

- `SyncStatus` adds context to the raw badge:
  - `not_requested`: written only after confirmation;
  - `pending`: queued for the worker;
  - `synced`: the event exists in the Maulwurf calendar;
  - `failed`: external edit or failed update; resolved in Google, never retried
    automatically;
  - `blocked`: Calendar is not ready; offers `reconectar` when a calendar is bound and
    `conectar` otherwise.
- `failed` is info-only. The M4 contract has no retry route, so the UI never implies one.
- `GoogleReconnect` renders the Google status, `calendar_write_ready`, the target label and
  a real anchor (`/integrations/google/reconnect` when a grant/calendar exists, otherwise
  `/integrations/google/connect`).
- Settings reads `?calendar=connected` / `?calendar=error&reason=`, consumes the params so a
  refresh does not repeat the banner, and states that reconnecting returned blocked tasks to
  `pending` without confirming anything. Unknown reasons never echo the query string.
- Tareas shows the compact banner while `calendar_write_ready` is false.
- Nothing in this ticket calls Google or confirms a task.

## 6. Evidence

See `docs/sprints/artifacts/D3.7/c-s3-da-08.txt`.

The first real attempts failed with `403 google_calendar_forbidden` on `calendarList` even
though the callback carried the three Calendar scopes. The cause was project configuration:
the Google Calendar API was not enabled for the OAuth client's Cloud project. After
enabling it and retrying reconnect, `calendarList` and `POST /calendars` returned `200`, the
calendar ID was stored and `calendar_write_ready` became true. No code change was needed.
