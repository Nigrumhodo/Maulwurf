## 1. Ticket summary

- **Objective:** an `infra/Caddyfile` that serves `web` + `api` + `ingest` under the same
  origin with local TLS, guaranteeing that large uploads are streamed **without buffering
  to disk, without cache and without body capture**.
- **Scope:** Caddyfile, routing by method/path (including `PUT /audios/{id}/content`),
  `internal` TLS, logs without bodies, no-buffering test.
- **Out of scope:** hardening `ingest` (J1.2), Redis policy (J1.6), effective size/time
  limits (D4/spike), authentication (A1.x).
- **Typed dependency:** `code` J1.1 (`caddy` service in compose). `contract` §1.2 of
  [../S1.md](../S1.md) for the binary `PUT` route.
- **Deliverables:** the definitive S1 `infra/Caddyfile`; script/checklist for the
  I-S1-JF-02 test with redacted evidence.
- **Acceptance criteria:**
  - [ ] `https://localhost` serves web and API under the same origin; `http://localhost`
    redirects.
  - [ ] `PUT /audios/{id}/content` is routed to the correct service and streamed.
  - [ ] The progress SSE is not buffered (`flush_interval -1`).
  - [ ] After uploading a large file, no filesystem of the proxy container gains files
    and the logs do not contain the body.
- **Tests/evidence:** **I-S1-JF-02** (proxy no-buffering on a large upload) with command,
  date, environment and result; without keeping the file used (generated in RAM).
- **Planned files:** `infra/Caddyfile`, `scripts/load/proxy_no_buffering.sh` (or
  `infra/tests/`), logbook.

## 2. Delivery design

### 2.1 Proposed Caddyfile

```caddyfile
{
	admin off
}

https://localhost {
	tls internal

	# 1) Ingestion binary PUT: pure streaming, no compression or buffering.
	@upload {
		method PUT
		path /audios/*/content
	}
	handle @upload {
		reverse_proxy ingest:8000 {
			flush_interval -1
		}
	}

	# 2) Progress SSE: immediate flush per event.
	@progress path /audios/*/progress
	handle @progress {
		reverse_proxy api:8000 {
			flush_interval -1
		}
	}

	# 3) JSON API (includes POST /audios and the rest of S1 M1/M2).
	#    /readyz is exposed for the I-S1-JF-01 smoke; /healthz stays internal only.
	@api path /auth/* /me /me/* /subjects /subjects/* /integrations/* /audios /audios/* /ingestion/* /readyz
	handle @api {
		reverse_proxy api:8000
	}

	# 4) Web (fallback).
	handle {
		reverse_proxy web:3000
	}

	log {
		output stdout
		format json
	}
}
```

Design rules:

1. **Routing by `handle`** (mutually exclusive) so that `PUT .../content` does not fall
   into the generic `/audios/*` matcher; the order of the `handle` blocks matters.
2. **No `encode`**: do not enable compression in S1 (avoids buffering of SSE responses
   and uploads; the saving is not a local requirement).
3. **No `request_buffers` or `request_body max_size`**: Caddy streams by default;
   the byte limits are validated by the application (contract §1.2) to return `413` with
   its own semantics.
4. **No cache**: Caddy does not cache by default; no cache plugin is added and the app's
   `Cache-Control` headers are not overridden (`GET /me` is `no-store`).
5. **No body capture**: the default JSON access log does not record bodies; it is
   documented that `log_append` and request body logging are not enabled.
6. **Local TLS:** `tls internal` issues a certificate from Caddy's local CA (persisted in
   `caddy_data`). There are no secrets; document how to trust the CA or use `curl -k`
   (J1.7).
7. **No admin API published:** `admin off`; port 2019 is not mapped.
8. **Timeouts:** do not set a short `read_body` that breaks uploads of up to 3 h (D4
   pending); keep the default and note the decision as provisional.
9. **Health:** API `/readyz` is routed through the same origin for the I-S1-JF-01 smoke;
   per-process `/healthz` is not published and is queried inside the container.

### 2.2 S1 vs S2 routing (coordination point)

In S1, A1.8 exposes `POST /audios` **and** a skeleton `PUT` in the API; real reception
arrives in S2 in `ingest`. The Caddyfile must allow switching the `PUT` from `api:8000`
to `ingest:8000` in one line. Recommendation: keep the `@upload` matcher pointing at
`ingest:8000` only once S1.B1 exposes the route; until then point it at `api:8000` and
record the change in the PR (do not duplicate routes across two services).

## 3. Step by step

1. Claim in `CLAIMS.md` and branch `s1/j1.3-caddy-no-buffering`.
2. Start from the minimal J1.1 Caddyfile and apply §2.1.
3. Validate the configuration without bringing everything up:
   ```bash
   docker run --rm -v "$PWD/infra/Caddyfile:/etc/caddy/Caddyfile:ro" caddy:2.8-alpine caddy validate --config /etc/caddy/Caddyfile
   ```
4. Bring up and check same-origin and TLS:
   ```bash
   cd infra && docker compose up -d caddy
   curl -kI https://localhost/            # web
   curl -kI https://localhost/me          # api (401 without session, not 404)
   curl -kI http://localhost/             # redirect to https
   ```
5. Prepare the no-buffering test (marker and initial state):
   ```bash
   docker compose exec caddy sh -lc 'touch /tmp/marker; df -h /tmp'
   BEFORE=$(docker inspect -f '{{.State.Pid}}' $(docker compose ps -q caddy))
   docker compose exec caddy sh -lc 'cat /sys/fs/cgroup/io.stat 2>/dev/null || true'
   ```
6. Upload a large stream generated in RAM (never versioned or persisted):
   ```bash
   head -c $((512*1024*1024)) /dev/zero | \
     curl -k -X PUT -H 'Content-Type: application/octet-stream' \
       --data-binary @- https://localhost/audios/smoke/content?attempt_id=smoke -o /dev/null
   ```
   If the real endpoint does not exist yet, use the test upstream agreed with A/S and
   record the limitation; the object of the test is Caddy, not the endpoint logic.
7. Verify that no files or bodies appeared:
   ```bash
   docker diff $(docker compose ps -q caddy)   # only expected changes in /data and /config
   docker compose exec caddy sh -lc 'find / -xdev -newer /tmp/marker -type f 2>/dev/null'
   docker compose exec caddy sh -lc 'ls -l /proc/*/fd 2>/dev/null | grep -i deleted || true'
   docker compose logs caddy | grep -c 'BEGIN\|multipart\|filename=' || true   # expected: 0
   ```
8. Repeat with the SSE if it already exists (long-lived connection; check that events
   arrive without waiting for the close).
9. Record evidence, logbook and PR.

## 4. Verification and evidence

- Minimum evidence: command of the load, transmitted size, `docker diff` with no new
  data files, `find` with no results, cgroup `io.stat` with no growth attributable to
  the body (exclude certificate writes), logs without body.
- Do not keep the test file: it is generated with `head -c /dev/zero` on the spot.
- Note explicitly the exclusion of `/data` and `/config` (certificates and autosave,
  not request content).

## 5. Coordination and risks

- **Route of the `PUT`:** it depends on A1.8 (S1) and on the real S2 reception; the
  matcher must stay isolated to switch without touching the rest.
- **`docker diff` false positive:** Caddy writes certificates to `/data`; the criterion
  is "no request data files", not "zero files".
- **Caddy without `encode`:** if compression is enabled later, exclude
  `text/event-stream` and the upload path.
- **`flush_interval -1`** is needed for SSE; document it so it is not removed in a later
  "cleanup".
