## 1. Ficha del ticket

- **Objetivo:** `infra/Caddyfile` que sirva `web` + `api` + `ingest` bajo el mismo origen con
  TLS local, garantizando que los uploads grandes se transmiten en streaming **sin buffering a
  disco, sin caché y sin captura de bodies**.
- **Alcance:** Caddyfile, ruteo por método/ruta (incluido `PUT /audios/{id}/content`), TLS
  `internal`, logs sin bodies, prueba de no-buffering.
- **No alcance:** endurecer `ingest` (J1.2), política Redis (J1.6), límites efectivos de
  tamaño/tiempo (D4/spike), autenticación (A1.x).
- **Dependencia tipada:** `código` J1.1 (servicio `caddy` en compose). `contrato` §1.2 de
  [../S1.md](../S1.md) para la ruta del `PUT` binario.
- **Entregables:** `infra/Caddyfile` definitivo de S1; script/checklist de la prueba
  I-S1-JF-02 con evidencia redactada.
- **Criterios de aceptación:**
  - [ ] `https://localhost` sirve web y API bajo el mismo origen; `http://localhost` redirige.
  - [ ] `PUT /audios/{id}/content` se enruta al servicio correcto y se transmite en streaming.
  - [ ] El SSE de progreso no se bufferea (`flush_interval -1`).
  - [ ] Tras subir un archivo grande, ningún filesystem del contenedor proxy gana archivos y
    los logs no contienen el body.
- **Pruebas/evidencia:** **I-S1-JF-02** (no-buffering del proxy en upload grande) con comando,
  fecha, entorno y resultado; sin conservar el archivo usado (se genera en RAM).
- **Archivos previstos:** `infra/Caddyfile`, `scripts/load/proxy_no_buffering.sh` (o
  `infra/tests/`), bitácora.

## 2. Diseño de la entrega

### 2.1 Caddyfile propuesto

```caddyfile
{
	admin off
}

https://localhost {
	tls internal

	# 1) PUT binario de ingesta: streaming puro, sin compresión ni buffering.
	@upload {
		method PUT
		path /audios/*/content
	}
	handle @upload {
		reverse_proxy ingest:8000 {
			flush_interval -1
		}
	}

	# 2) SSE de progreso: flush inmediato por evento.
	@progress path /audios/*/progress
	handle @progress {
		reverse_proxy api:8000 {
			flush_interval -1
		}
	}

	# 3) API JSON (incluye POST /audios y el resto de M1/M2 de S1).
	#    /readyz se expone para el smoke I-S1-JF-01; /healthz queda solo interno.
	@api path /auth/* /me /me/* /subjects /subjects/* /integrations/* /audios /audios/* /ingestion/* /readyz
	handle @api {
		reverse_proxy api:8000
	}

	# 4) Web (fallback).
	handle {
		reverse_proxy web:3000
	}

	log {
		output stdout
		format json
	}
}
```

Reglas de diseño:

1. **Routing por `handle`** (mutuamente excluyentes) para que `PUT .../content` no caiga en el
   matcher genérico de `/audios/*`; el orden de los `handle` importa.
2. **Sin `encode`**: no habilitar compresión en S1 (evita buffering de respuestas SSE y de
   uploads; el ahorro no es requisito local).
3. **Sin `request_buffers` ni `request_body max_size`**: Caddy hace streaming por defecto;
   los límites de bytes los valida la aplicación (contrato §1.2) para devolver `413` con
   semántica propia.
4. **Sin caché**: Caddy no cachea por defecto; no se agrega plugin de caché ni se sobreescriben
   `Cache-Control` de la app (`GET /me` es `no-store`).
5. **Sin captura de bodies**: el access log JSON por defecto no registra cuerpos; se documenta
   que no se habilita `log_append` ni logging de request body.
6. **TLS local:** `tls internal` emite certificado de la CA local de Caddy (persistida en
   `caddy_data`). No hay secretos; documentar cómo confiar en la CA o usar `curl -k` (J1.7).
7. **Sin admin API publicado:** `admin off`; no se mapea el puerto 2019.
8. **Timeouts:** no fijar un `read_body` corto que rompa uploads de hasta 3 h (D4 pendiente);
   dejar el default y anotar la decisión como provisional.
9. **Salud:** `/readyz` de API se enruta por el mismo origen para el smoke I-S1-JF-01;
   `/healthz` por proceso no se publica y se consulta dentro del contenedor.

### 2.2 Enrutamiento S1 vs S2 (punto de coordinación)

En S1, A1.8 expone `POST /audios` **y** un `PUT` esqueleto en la API; la recepción real llega
en S2 en `ingest`. El Caddyfile debe permitir conmutar el `PUT` de `api:8000` a `ingest:8000`
en una línea. Recomendación: dejar desde ya el matcher `@upload` apuntando a `ingest:8000`
solo cuando S1.B1 exponga la ruta; hasta entonces apuntar a `api:8000` y registrar el cambio
en el PR (no duplicar rutas en dos servicios).

## 3. Paso a paso

1. Claim en `CLAIMS.md` y rama `s1/j1.3-caddy-no-buffering`.
2. Partir del Caddyfile mínimo de J1.1 y aplicar §2.1.
3. Validar la configuración sin levantar todo:
   ```bash
   docker run --rm -v "$PWD/infra/Caddyfile:/etc/caddy/Caddyfile:ro" caddy:2.8-alpine caddy validate --config /etc/caddy/Caddyfile
   ```
4. Levantar y comprobar same-origin y TLS:
   ```bash
   cd infra && docker compose up -d caddy
   curl -kI https://localhost/            # web
   curl -kI https://localhost/me          # api (401 sin sesión, no 404)
   curl -kI http://localhost/             # redirección a https
   ```
5. Preparar la prueba de no-buffering (marcador y estado inicial):
   ```bash
   docker compose exec caddy sh -lc 'touch /tmp/marker; df -h /tmp'
   BEFORE=$(docker inspect -f '{{.State.Pid}}' $(docker compose ps -q caddy))
   docker compose exec caddy sh -lc 'cat /sys/fs/cgroup/io.stat 2>/dev/null || true'
   ```
6. Subir un flujo grande generado en RAM (nunca versionado ni persistido):
   ```bash
   head -c $((512*1024*1024)) /dev/zero | \
     curl -k -X PUT -H 'Content-Type: application/octet-stream' \
       --data-binary @- https://localhost/audios/smoke/content?attempt_id=smoke -o /dev/null
   ```
   Si el endpoint real no existe aún, usar el upstream de prueba acordado con A/S y registrar
   la limitación; el objeto de la prueba es Caddy, no la lógica del endpoint.
7. Verificar que no aparecieron archivos ni bodies:
   ```bash
   docker diff $(docker compose ps -q caddy)   # solo cambios esperados en /data y /config
   docker compose exec caddy sh -lc 'find / -xdev -newer /tmp/marker -type f 2>/dev/null'
   docker compose exec caddy sh -lc 'ls -l /proc/*/fd 2>/dev/null | grep -i deleted || true'
   docker compose logs caddy | grep -c 'BEGIN\|multipart\|filename=' || true   # esperado: 0
   ```
8. Repetir con el SSE si ya existe (conexión larga, comprobar que los eventos llegan sin
   esperar el cierre).
9. Registrar evidencia, bitácora y PR.

## 4. Verificación y evidencia

- Evidencia mínima: comando de la carga, tamaño transmitido, `docker diff` sin archivos
  nuevos de datos, `find` sin resultados, cgroup `io.stat` sin crecimiento atribuible al body
  (excluir escritura de certificados), logs sin body.
- No conservar el archivo de prueba: se genera con `head -c /dev/zero` en el momento.
- Anotar explícitamente la exclusión de `/data` y `/config` (certificados y autosave, no
  contenido de requests).

## 5. Coordinaciones y riesgos

- **Ruta del `PUT`:** depende de A1.8 (S1) y de la recepción real de S2; el matcher debe
  quedar aislado para conmutar sin tocar el resto.
- **Falso positivo del `docker diff`:** Caddy escribe certificados en `/data`; el criterio es
  «ningún archivo de datos de request», no «cero archivos».
- **Caddy sin `encode`:** si más adelante se habilita compresión, excluir
  `text/event-stream` y el path de upload.
- **`flush_interval -1`** es necesario para SSE; documentarlo para que no se elimine en un
  «cleanup» posterior.
