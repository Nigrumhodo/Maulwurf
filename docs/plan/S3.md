## 0. Objective and exit gate

**Objective:** task proposal → human review → confirmation → **a single event** in
Google Calendar; calendar reading and confirmed editing; read-only chat tools.
**No write happens without explicit human confirmation.**

**Exit gate — the sprint does NOT close without all of this:**

1. E2E with a test Google account: proposal → review → confirmation → event visible
   exactly once.
2. Double click, lost response, and concurrent retries **do not duplicate** the event.
3. All-day vs timed handled correctly (exclusive date pairs vs start/end with IANA
   timezone).
4. Scope rejection does not break the library or chat (`blocked` visible, not an error).
5. G5-F2, G6, and G7-CAL approved: ≥50 annotated activities per language, precision ≥ 0.95,
   recall ≥ 0.85, exact date ≥ 0.95 on solvable cases, and evidence validated 100%.
6. D7-CAL findings documented with real calls; the evaluation uses a frozen test dataset,
   metric, and numerator/denominator per language.

**Interfaces frozen on Monday:** the `tasks` + revisions (`task_revisions`) contract; shape
of `calendar_events`; read chat tools (`get_calendar_events`, `get_pending_tasks`,
`propose_task`) with their iteration limits; prompts v1.

## 1. Frozen contracts (exact reference)

### 1.1 Task (M4 shape) — provider: API/DB · consumers: RAG, Web, Infra

Fields: `id`, optional `audio_id`, normalized `sources[]` (`audio_id`, transcript version,
segment, and span), `subject`, `source` (`extraction|manual|chat`), type/title/detail,
`due_date` **XOR** `due_at`, timezone/all-day/date status/confidence, task status, and a
separate `calendar_sync_status`. `version`/`due_version` control concurrency. The Calendar
block persists `event_start_at/event_end_at` **or**
`event_start_date/event_end_date_exclusive`, exclusive pairs with a later end; it may stay
empty until confirmation. The default duration is visible/editable and never invented by
the LLM. `pending_revision` contains `id`, `base_task_version`, `proposed_fields`, and
status `pending_confirmation|activated|discarded`.

### 1.2 M4 endpoints — provider: API/DB

`GET /tasks?status=&subject_id=&due_from=&due_to=` · `GET /tasks/{id}` · `POST /tasks`
(manual uses zero sources; chat/corpus requires validated sources) · `PATCH /tasks/{id}` with
`version` (if it was confirmed, creates a revision without mutating the active fields) ·
`POST /tasks/{id}/confirm` with `{expected_version, revision_id?}` (promotes exactly that
revision, task+outbox atomic, valid date/block/evidence; `409 version_conflict`; without the
integration it stays `blocked`) · dismiss/complete cancel future reminders and keep the
event unless there is an explicit remote operation.

### 1.3 Calendar (M5 shape) — provider: Infra

`GET /calendar/events?from=&to=` reads the **local mirror** `calendar_events` (proposed
window of -7/+60 days; reports `last_synced_at` and coverage). `POST /calendar/sync` forces
a full refresh with atomic publication (never mixing `syncToken` with filters).
`GET /calendar/conflicts` distinguishes: `time_conflicts` (overlap of timed events) ≠
`deadline_clashes` (deadlines/exams clustering on the same day). The same contract feeds the
dashboard and the `get_calendar_events(range)` chat tool.

J3.7 fixes the read shape: `from`/`to` are inclusive local dates; the response adds
`from`, `to`, `last_synced_at`, `coverage_ok`, `stale` and a closed-set `coverage_notice`
(`never_synced`, `no_read_calendars`, `calendar_set_changed`, `outside_coverage`, `stale`).
Events keep instants or the exclusive all-day pair, never both.

### 1.4 Read-only chat tools — provider: RAG · consumers: Infra (runner), Web

Allowlist: `get_calendar_events(range)`, `get_pending_tasks()`, `propose_task(...)`.
None of them writes to Calendar or sends email; capped iteration/time budget; ranges and
schemas validated by the backend (never trust the LLM output); `propose_task` creates a
proposal in the inbox (`source: chat`), never schedules directly.

## 2. RAG tickets (`L3.x`)

### L3.1 — Versioned prompts v1

**Depends on:** L1.4 · **Tests:** R-S3-JL-06.

How it must work: directory `apps/api/prompts/v1/` with extraction system/user prompts; each
prompt registered with its `prompt_version` in the analysis results; regression tests in CI
that run **against recorded LLM outputs** (no keys or PII, no quota spent). Rule: a prompt
change without green regression tests does not ship.

### L3.2 — Final Pydantic schema §M4

**Depends on:** L1.4 · **Tests:** U-S3-JL-01.

Freezes the §1.1 schema: types, `due_date`/`due_at` exclusivity, `date_status`,
`confidence_score`, Unicode spans `[start, end)`, and a mandatory verbatim quote per piece
of evidence. Delivered on day 1 — A3.1 builds the table on top of this contract.

### L3.3 — Deterministic post-LLM validation

**Depends on:** L3.2 · **Tests:** U-S3-JL-01/02.

How it must work: after every LLM response, validation that **does not trust it**: enums and
ranges; membership of each cited segment in the correct class/tenant/version; Unicode spans
within range (outside → rejection); **literal** check of the verbatim quote against the
segment reconstructed from the DB (the `quote` must exist exactly in the segment).
Deliverable: zero proposals with an invented span or quote.

### L3.4 — Date resolution against the class

**Depends on:** L3.2 · **Tests:** U-S3-JL-03.

How it must work: resolve dates against the **class date and timezone** (not the upload's,
not the server's "today"). Mandatory coverage: DST (nonexistent hour → next valid instant;
repeated hour → only once), relatives ("next Friday"), ambiguity → `needs_review` with
`date_status=ambiguous`; **never an invented midnight** as the due time; impossible dates
rejected. Injectable clocks in tests.

### L3.5 — Windows with overlap and dedupe

**Depends on:** S3.4 · **Tests:** U-S3-JL-04.

How it must work: analysis over transcript windows with overlap; aggregation with task
dedupe by **identical evidence** (same segment+range+quote); idempotency guaranteed by
`processing_runs` (the same run does not reproduce duplicates).

### L3.6 — `analyze(audio_id)` and backend tool orchestrator

**Depends on:** J2.2 (generic runner), A3.1 (data contract) · **Tests:** U-S3-JL-05,
I-S3-AN-04.

On day 1 it delivers the contract/double so S3.1 can prepare the backfill; the first
integrable implementation arrives on day 3. `analyze` is a pure function wrapped by the
worker, creates revisions without overwriting edited/confirmed tasks, and publishes no
partials. It also implements the backend orchestrator for `get_calendar_events`,
`get_pending_tasks`, and `propose_task`: allowlist, tenant from the session, validated
schemas/ranges, capped iterations/time, and zero Calendar/email writes. `propose_task` uses
`task_sources` or is flagged as a general suggestion without evidence.

### L3.7 — G6 evaluation

**Depends on:** L3.1–L3.5 · **Tests:** R-S3-JL-06 (CI), P-S3-JL-07 (real, protected).

How it must work: dataset of ≥50 annotated activities per language (ambiguities and DST
included); metrics: precision ≥ 0.95, recall ≥ 0.85, exact date ≥ 0.95 on solvable cases,
evidence validated 100%. The `R-` runs in CI with recorded outputs; the `P-` is the real
protected measurement with a budget.

### L3.8 — Versioned summary and topics

**Depends on:** L3.1 · **Tests:** R-S3-JL-06.

A 3–5 sentence summary and a topic list per class, with versioned shape/prompt (consumed by
D3.5). The regression validates that the recorded output respects the schema and contains no
sensitive data.

## 3. API/DB tickets (`A3.x`)

### A3.1 — Complete `tasks` table

**Depends on:** A2.1; L3.2 (contract) · **Tests:** U-S3-AN-01.

How it must work: `tasks`, `task_sources`, and `task_revisions` with tenant-aware FKs; CHECKs
for date, confidence, statuses, Calendar block, and `base_task_version`. Active fields
include `event_start/end_*`; the revision keeps `proposed_fields` and
`pending_confirmation`. Use the two partial indexes `(user_id,status,due_at)` and
`(user_id,status,due_date)`, never `COALESCE(date::timestamptz)`. One coherent migration,
no emergencies.

### A3.2 — Persisted evidence and provenance

**Depends on:** A3.1 · **Tests:** I-S3-AN-05.

Each piece of evidence stores transcript/segment/span/quote; `task_sources` normalizes one
or more sources per task. `date_text`, `date_reason`, `due_version`, and a timezone snapshot
are persisted. A manual task uses zero sources; chat/extraction based on the corpus requires
at least one validated source. Criterion: evidence and provenance 100% reconstructible from
the DB.

### A3.3 — M4 endpoints with optimistic locking

**Depends on:** A3.1 · **Tests:** U-S3-AN-02.

All endpoints from §1.2. `PATCH` requires `version`; on a confirmed task it creates a
revision `pending_confirmation`, without mutating active fields or writing to Google;
mismatch → `409` with the current status. `POST /tasks` validates the source type and never
allows presenting an evidence-free suggestion as an extraction.

### A3.4 — Atomic confirmation

**Depends on:** A3.3, J1.5 (outbox) · **Tests:** I-S3-AN-03.

How it must work: `confirm({expected_version, revision_id?})` validates that the revision
belongs to the task and starts from the active version; it promotes its fields only in the
transaction that bumps the version and creates/reuses `calendar.event.sync`. A double click
produces one outbox per `task_id+due_version`; a stale revision → `409`. Without Google:
confirmed+`blocked`, not an error. Requires a date, Calendar block, and evidence where
applicable.

### A3.5 — Re-analysis creates a new revision

**Depends on:** A3.1 · **Tests:** I-S3-AN-04.

How it must work: re-analysis neither deletes nor overwrites edited/confirmed tasks; it
creates a `pending_confirmation` revision with `base_task_version`. The user compares and
confirms; only then is it activated. Double analysis does not duplicate.

### A3.6 — Evidence reconstruction from the DB

**Depends on:** L3.3 · **Tests:** I-S3-AN-05.

How it must work: a module that rebuilds the segment text from the DB with Unicode offsets
and validates the L3.3 spans (invalid membership rejected). It is the backend counterpart of
RAG validation: **no proposal persists with a span or quote that cannot be reconstructed**.

### A3.7 — Status rules

**Depends on:** A3.3 · **Tests:** I-S3-AN-03.

Confirming requires a resolved or confirmed date, a valid Calendar block, and verified
evidence for extracted ones. `scheduled` is never a task status; sync is remote.
`blocked → pending` only happens when reconnecting with a current version. Task, revision,
and sync transitions are tested as origin/command/destination tables.

### A3.8 — Calendar settings and the `calendar_events` mirror

**Depends on:** A3.1 · **Tests:** I-S3-JF-05.

Creates per-user `settings` with the writing calendar and the selected reading calendars,
and `calendar_events` keyed by `(user_id,calendar_id,event_id)`, all-day kept separate,
ETag, and coverage/freshness. The Gmail/digest extension arrives in S4. Ready for
J3.3/J3.7 with atomic publication.

### A3.9 — Idempotency tests

**Depends on:** A3.4 · **Tests:** I-S3-AN-06.

Double analysis does not duplicate tasks (dedupe by evidence); concurrent editing does not
lose data (409 + refresh); double confirmation does not create a duplicate outbox.

## 4. Ingest/ASR tickets (`S3.x`)

### S3.1 — Analysis backfill for F1 classes

**Depends on:** L3.6 (contract/double on day 1; integration on day 3), A3.1 ·
**Tests:** I-S3-SG-01.

How it must work: retrospective analysis of classes already transcribed in S2 **only from
persisted text** — never a reupload or retranscription; explicit queue visible on the class

Implementation status (2026-10-31): the explicit queue and its operator script exist

### S3.2 — Efficient windows with measured cost

**Depends on:** S3.1 · **Tests:** U-S3-SG-02.

How it must work: windows with efficient overlap (bounded token cost) and dedupe by

Implementation status (2026-10-31): `app/services/analysis_windows.py` plans sentence-aligned

### S3.3 — Robustness without ASR offsets

**Depends on:** S3.1 · **Tests:** U-S3-SG-03.

How it must work: if D6 decided `none` (or a transcript has no times), the analysis still
works with textual evidence (no `t_start/t_end`); **zero invented minutes**; the UI shows
"segment N".

Implementation status (2026-10-31): `apps/api/app/services/evidence.py` is the shared
no-offset path. `reliable_times` withholds both times for `timestamp_precision=none`,
incomplete/non-finite/inverted pairs, and pairs past the class duration; search hydration,
RAG source blocks and citations use the same policy. `evidence_reference` returns a measured
`mm:ss` only when the pair is truthful and otherwise `"segment N"`, and
`resolve_textual_evidence` rebuilds the segment, Unicode span and verbatim quote with null
times. U-S3-SG-03 covers the no-offset and mixed-transcript cases, including that no
neighbour time is interpolated and `00:00` is never used as a fallback. L3.6's `analyze` and
A3.1's task tables are not in `develop`, so this ticket claims the evidence layer, not
extraction output; the D3 inbox and its web rendering are out of scope here.

### S3.4 — `processing_runs` per version

**Depends on:** S3.1 · **Tests:** I-S3-SG-04.

How it must work: each run records the transcript version and the configuration/prompt
version; re-analysis only reprocesses what is necessary (a new run if the version changed);
old runs remain queryable.

Implementation status (2026-10-31): `processing_runs` is the durable per-class ledger
(`app/models/processing_run.py`). `RunSpec` in `app/services/runs.py` fixes the identity of a
run: the stage, the transcript version it reads and the stage configuration version; an
`analyze` run also persists its `prompt_version` and derives the config version from it, so
a prompt bump always creates a new run. Retry/backfill reuse a row only when all versions
match; otherwise they insert a NEW row and never reset or overwrite the previous one. The
derived stage state and the backfill availability now ignore runs of other transcript/config
versions, so a version change is visible as owed reanalysis instead of being masked by a
stale `succeeded`. The availability also mirrors `classify_existing_run` for an F2 class
without any analysis run: the class page reports `analysis_backfill_available: false` and
routes it to `POST /audios/{id}/retry`, never to a backfill that answers
`already_f2_no_run`. Old runs stay queryable through the tenant-scoped
`GET /audios/{id}/runs` history. I-S3-SG-04 covers the ledger, version change, tenant
isolation and the endpoint. Local gates are green (ruff/mypy, 944 API unit); the local
sandbox has no PostgreSQL/Redis, so the integration evidence is Quality CI run
`41206730192` on head `c204954`: all 17 checks green, `python-unit (api)` 944 passed and
`integration (api)` 416 passed, including the new F2-without-run availability case.

### S3.5 — Cost measurement

**Depends on:** S3.2 · **Tests:** basis for C-S4-SG-04.

Table: ASR cost (effective minutes × rate measured in the spike) and RAM/tmpfs under load.
Basis for the final S4.5 table.

Implementation status (2026-10-31): `scripts/load/asr_cost.py` measures the audio seconds
actually billed to ASR (fragment spans including the configured overlap) and the RAM/tmpfs
working set of concurrent ingestion slots. It runs the production `pipeline.process` audio

key or provider call is involved. At the defaults (30 s fragment cap, 0.25 s overlap) a
300 s clip produces 11 fragments and 302.5 billed seconds per slot: **60.5 effective

the ffmpeg child peaks at 47.85 MiB (single-child maximum, not additive). The F0.1 report
leaves `Cost per minute` and `Cost per hour` as `NO VERIFICADO`, so the cost per class hour

published in [`docs/eval/asr-cost.md`](../eval/asr-cost.md) with the raw capture in

passing. Quality CI runs `41209918176` (head `4727443`) and `41210214297` (head `d4fe3d9`) are green in all 17

### S3.6 — Retry hardening

**Depends on:** S3.1 · **Tests:** U-S3-SG-05.

Bounded backoff+jitter (max 3 transients) for analysis; **ASR quality warnings** (low
confidence, empty segments) visible to the inbox (D3.1). The unit test covers error
classification and backoff; warning display is verified with C-S3-DA-01.

Implementation status (2026-10-31): `app/workers/retry.py` is the pure decision core for
the analysis job: `classify_analysis_error` treats provider 408/429 and 5xx responses,
transport timeouts, lost connections and PostgreSQL serialization/deadlock failures as
transient; provider 4xx responses other than 408/429 (bad key, missing model, malformed
prompt), protocol/configuration errors (`httpx.UnsupportedProtocol`,
`httpx.LocalProtocolError`), PostgreSQL authentication failures (SQLSTATE `28P01`) and
everything else as permanent (fail closed). A provider error without an HTTP status is
permanent unless the adapter reports a known transient transport failure (`ConnectError`,
`ConnectTimeout`, `ReadError`, `ReadTimeout`, `WriteTimeout`, `PoolTimeout`,
`RemoteProtocolError`, `TimeoutException`); the adapter's parse/protocol reasons
(`invalid_sse_json`, `invalid_sse_payload`, `stream_error`, `missing_choices`,
`invalid_choice`, `non_text_delta`, `invalid_max_tokens`) therefore never retry.
`retry_decision` allows one delivery plus **three transient retries** with the existing
bounded backoff+jitter policy, then reports `retry_exhausted`; a permanent error is never
retried. The persisted `error_code` comes from
a closed allowlist, so an arbitrary provider/driver attribute is never written. The ARQ
`analyze` entry point declares that same `MAX_TRIES` budget, so L3.6 inherits it when the
analyzer lands. U-S3-SG-05 also covers the ingestion side: `persistence.quality_warnings`
marks `empty_segments` and `low_confidence` (only when the provider actually reported
confidence; at least half of the scored words below the provisional threshold) next to the
existing `repetition` signal, without storing spoken words. `GET /audios/{id}` exposes the
normalized `transcript.quality_warnings` (`code` restricted to the ingestion allowlist
`repetition`/`empty_segments`/`low_confidence`, plus counts; unknown codes and fields
dropped), the signal D3.1/D3.5 consume. C-S3-DA-01 is a Web/manual checklist and is **not**
executed here: `apps/web` is untouched and D3.1 remains out of this claim. L3.6's analyzer is
absent from `develop`, so no extraction output or real provider call is claimed. Explicit
debt for L3.6: while `analyze` is a no-op the real retry path has no integration coverage,
and ARQ (`func(analyze, max_tries=4)`) does not itself skip permanent errors until the
analyzer consumes `retry_decision`; that wiring and its integration test are L3.6 scope.
Non-blocking review notes accepted on 2026-10-31: `persistence._valid_confidence` accepts
`0.0` while `riva_client` maps it to unknown at the protobuf boundary, so a provider that
reports `0.0` would count as low confidence (the Riva rule stays provider-local until a
global confidence contract is decided); `normalize_quality_warnings` does not reject
`count > total`; and `empty_segments` counts empty words, not segments, while the wire code
is kept because D3.1 consumes it.

### J3.2 — `GoogleCalendarService`

**Depends on:** J3.1 · **Tests:** P-S3-JF-02.

How it must work: blocking client isolated from the event loop; bounded retries for 429/5xx
**respecting `Retry-After`**; `invalid_grant` disconnects the integration (not every 403 is
retryable); errors classified transient/non-transient.

Implementation status (2026-10-31): `apps/api/app/services/google_calendar.py` adds
`GoogleCalendarService`, a minimal Calendar client whose synchronous `httpx.Client` runs
inside `asyncio.to_thread`; retry sleeps happen in that worker thread, so a slow Calendar
call never blocks the event loop. Retries are bounded (`max_retries + 1` attempts) and
limited to 408/429/5xx, network errors and the Google 403 quota reasons
(`rateLimitExceeded`, `userRateLimitExceeded`, `quotaExceeded`, `dailyLimitExceeded`,
`backendError`, `RESOURCE_EXHAUSTED`); a plain 401/403, 404, 409 or other 4xx is terminal.
`Retry-After` is honoured in numeric-seconds and HTTP-date form, capped by
`max_retry_after_seconds`, and replaces the exponential backoff with jitter. Errors are
typed with `transient`/`disconnects_integration` flags. A structured `invalid_grant`
(string or `errors[].reason`) invokes `on_invalid_grant` once, never retries, and raises
`GoogleCalendarInvalidGrant`; `disconnect_google_credential` is the ready-made callback that
flips `google_credentials.status` to `disconnected`. `tests/unit/test_google_calendar.py`
(21 cases) covers the deterministic P-S3-JF-02 contract: worker-thread isolation, numeric
and HTTP-date `Retry-After`, the cap, 5xx/network retries, 403 quota vs. forbidden,
`invalid_grant` disconnect, 401/404/409, request forwarding, invalid JSON, 204 and log
redaction. J3.1's protected-account scope verification is still pending, so the cloud leg of
P-S3-JF-02 is not executed and no real Google call or secret is involved; cloud eligibility
stays `pending`. Local gates: `ruff` and `mypy` clean, 994 API unit tests passed. The raw
capture, including the two unrelated httpx/`NO_PROXY` failures seen with the sandbox proxy
environment, is in [`docs/sprints/artifacts/J3.2/local-gates.txt`](../sprints/artifacts/J3.2/local-gates.txt).
No web change. Branch `task/MAULW-115`, PR #126.

### J3.4 — Idempotent `sync_task_event(task_id, task_version)` job

**Depends on:** A3.4 (outbox) · **Tests:** I-S3-JF-03.

How it must work: **deterministic** event ID derived from the task UUID
(hex/base32hex); insert timeout → query by that ID before retrying; 409 →
check identity and reconcile; jobs for stale versions are discarded. Result:
double submission/lost response → exactly one event.

Implementation status (2026-10-31): `app/services/task_event_sync.py` implements the
protocol with two ports (`TaskEventStore`, `CalendarGateway`). The event ID is `maul`
plus the lower-case base32hex of the 16 UUID bytes (30 characters, Google's `[a-v0-9]`
alphabet); a repeated delivery targets the same ID. A transient insert (timeout, 5xx,
429) is never treated as proof of failure: the engine `GET`s that ID first, adopts a
matching event, and only retries an absent one (bounded twice per delivery, then
`Retry` through ARQ). A 409 is reconciled only when the event's private
`maulwurfTaskId` matches; a foreign event is left untouched and the task becomes
`failed`. `calendar_sync_status`/`calendar_event_id` are written with a compare-and-set

### J3.7 — Calendar reading + `GET /calendar/events`

**Depends on:** A3.8 · **Tests:** I-S3-JF-05.

How it must work: -7/+60-day window with full pagination, expanded recurrences, deletions
applied; **atomic** publication into `calendar_events` (full replacement of the window in
one transaction); record coverage and `last_synced_at`; never mixing `syncToken` with
filters. Exposes the §1.3 `GET /calendar/events`.

Implementation status (2026-10-31): `app/services/calendar_sync.py` owns the read and the
publication. `CalendarWindow` computes the default window from the user's IANA zone
(seven local days back, sixty local days forward, inclusive end = next local midnight), so a
DST change does not shift the covered days. `GoogleCalendarEventSource` requests
`singleEvents=true` (recurrences expanded), `showDeleted=true` (deleted instances returned),
`orderBy=startTime` and the absolute `timeMin`/`timeMax`; it follows every `nextPageToken`
up to a bounded 100 pages and fails the whole read when the budget is exhausted. It never
sends `syncToken`; `build_list_params` rejects mixing it with the window filters instead of
silently dropping one side. A `status=cancelled` event is a deletion: it is not inserted, and
the full window replacement removes any previous row. Malformed events (missing pair, naive
instant, inverted range) fail the read rather than shrinking coverage silently.

`sync_calendar_window` reads every selected calendar **before** touching the database, then
`SqlCalendarMirror.replace_window` takes a per-user transaction advisory lock (two-int form
with namespace `0x4D57`, the A2.14 convention shared with `services/audios.py`), prunes the
republished calendars' rows that ended before the window, deletes the window rows the fresh
read no longer returns and upserts the complete result on `(user_id, calendar_id, event_id)`
inside one savepoint. The upsert lets an event rescheduled into the window from an earlier
publication update in place; a plain `INSERT` would violate the unique key and fail every
sync. Pruning bounds the mirror: Google is queried from `window.start`, so a row that ended
before the window can never be observed again. `source` and `task_id` are preserved on
conflict, and task-linked rows are never pruned because the write path owns them. It then
upserts `settings.calendar_last_synced_at`, `calendar_coverage_from`,
`calendar_coverage_to` and `calendar_coverage_calendar_ids`. A failure anywhere in the
savepoint leaves the previous mirror and the previous coverage untouched. Duplicate
`(calendar_id, event_id)` rows from an inconsistent page are collapsed before publication.

A3.8 is not in `develop`: migration `0006_s3_calendar_mirror` provisions the frozen
`settings` + `calendar_events` shape (DESIGN §2.8–§2.9), including forced RLS with the
`maulwurf_app` tenant policy and the `maulwurf_jobs` tenant/cross-tenant policies. The
`task_id` column has no composite FK because `tasks` (A3.1) does not exist yet; the unique
partial index for the one-to-one task link is already in place. This is dependency
provisioning, **not** an A3.8 closure; the A3.8 row stays unclaimed.

`GET /calendar/events?from=&to=` (`app/routers/calendar.py`, `app/schemas/calendar.py`)
reads only the local mirror. Parameters are inclusive local dates; the default is `-7/+60`,
and a lone bound anchors the window (`from` → `from+60`, `to` → `to-7`) instead of being
completed from today's default. The response is not paginated: the widest allowed window (366
days) and the per-user mirror bound it, and a silent `LIMIT` would report incomplete data as
covered. The response keeps the frozen `events` list and adds the freshness envelope consumed
by D3.6/J3.8:

```json
{
  "events": [],
  "from": "2026-10-24",
  "to": "2026-12-30",
  "last_synced_at": "2026-10-31T12:00:00Z",
  "coverage_ok": true,
  "coverage_notice": null,
  "stale": false
}
```

`coverage_notice` is a closed set: `null`, `never_synced`, `no_read_calendars`,
`calendar_set_changed`, `outside_coverage` or `stale` (older than two hours). The mirror is
still returned with a notice, never as a hard failure; `from > to` and a range wider than 366
days answer `422 validation_failed`.

Evidence: `tests/unit/test_calendar_read.py` (33 cases: window/DST math, half-given range
anchoring, query contract, non-object payloads, pagination, cancellation, normalization with
an unresolvable timezone, coverage, no-publication-on-failure) and
`tests/integration/test_calendar_read.py` (**I-S3-JF-05**, 17 cases against PostgreSQL:
publication + mirror read, full replacement with an outside-window row preserved, an event
reprogrammed from outside the window updated in place, pre-window pruning that spares
task-linked rows and unselected calendars, a task-linked row inside the window keeping its
link across refreshes (and surviving a refresh that no longer returns it), failed read with
no writes, mid-publication CHECK failure rolled back with the previous coverage intact,
tenant isolation, coverage notices, default window, lone `from`/`to`, 422/401, two-page
Google read with no `syncToken`, and an unknown tenant mirror). The read mirror never deletes
nor unlinks a task-linked row, even when the remote event disappears or moves out of the
window: those rows belong to the write path (J3.4/A3.8), and destroying the link would also
free the partial unique index `calendar_events_one_link`. Local gates: `ruff` and `mypy`
clean (224 files), **1188 unit** and **434 integration** passed; the 32 integration failures
are the pre-existing pgvector 0.6 `< 0.8` search/chat/G4 set (`500
search_hnsw_unsupported`), outside this diff. A Quality CI run on the review-fix head was
not observable from the development sandbox (no valid GitHub credentials); the previous run
