## Common normative ticket template

This template governs all tickets in this document. The stated area describes a capability or
a contract, **it does not assign a person**. Each ticket has a single owner, claimed when the
sprint opens via a merged row in [../sprints/CLAIMS.md](../sprints/CLAIMS.md); the logbook
only records evidence afterwards. Reviewers and support are expressed per area or role.

- **Objective:** the observable outcome the ticket must produce.
- **Scope / non-scope:** included behavior and exclusions that keep the ticket from growing.
- **Typed dependency:** classify each dependency as `contract`, `code`, `gate`,
  `external`, or `operational`; a blocking dependency must be available or replaced by a
  double against a frozen contract before starting.
- **Deliverables:** expected code, migration, document, decision, or reproducible artifact.
- **Criteria:** verifiable acceptance conditions, without presenting proposals as facts.
- **Tests / evidence:** linked test or, if none exists, the **Mandatory verification** section
  with a command, checklist, or artifact; record date, environment, version, and real result.
- **Expected files:** paths the owner declares when claiming; any scope change is
  updated before editing additional paths. The "Implementation Map" at the end of each
  sprint proposes indicative paths; the ticket's contract and deliverable do not change if the
  owner chooses another location.
- **Execution plan:** mandatory when the ticket crosses more than one layer or service; numbered
  steps with file/module, command if applicable, and expected result per step. A ticket with
  an incomplete execution plan is returned in review, not completed on the fly.

Tickets may use the existing compact form and reference this template without repeating it.
A `Depends on: —` means "no blocking dependency", not "no coordination or evidence".

**Objective:** a running monorepo, basic authentication, an initial migratable schema, and the
real NVIDIA Riva contract tested with evidence (spike F0.1) plus an ephemeral ingestion

4. Complete S1.B4 failure matrix (9 scenarios demonstrated, not just written down).
5. Decisions closed: D2 (Riva contract) · D3-Audio (retention/processing and consent) ·
   D4 (effective limits) · D6 (`word|segment|none`) with the **G2-T or G2-X gate variant
   chosen explicitly** and reflected in API/UI (if there are no reliable timestamps, G2-X is
   approved).
6. CI green on MR (lint, types, unit tests, integration with real services, builds).
7. Basic isolation proven: user B cannot see A's resources even when guessing IDs.
8. Static public landing page at `/` for visitors (D1.8), with no private data or secrets.

Hard rule: **no real class recordings are accepted before F0 and D3-Audio are closed.** The
spike uses authorized synthetic audio. If it does not produce reliable timestamps, the
product and architecture role decides D6 before S2 depends on it.

### 1.1 Opaque session and CSRF (responsible area: API/DB · consumer areas: all)

- Login: Google OAuth Authorization Code with `state` + PKCE; `nonce`, `issuer`,
  and `audience` are validated; the user identity is **always Google's `sub`, never the email**.
- Session cookie `mw_session`: `Secure`, `HttpOnly`, `SameSite=Lax`, random opaque value.
  The DB (`sessions`) stores **only the hash** of the identifier, with expiration and
  revocation; logout revokes it immediately.
- `GET /me` delivers the plain CSRF token in the body and responds `Cache-Control: no-store`;
  `sessions` keeps only `csrf_hash`. The token rotates when the session is created or rotated, is shared
  across the tabs of that session, and becomes invalid when the session is closed or revoked.
- Every mutating operation requires `X-CSRF-Token` and same-origin `Origin` validation,
  **including the binary upload**.
- Authentication errors: `401` with no session or with a revoked/expired session; the client
  responds by redirecting to login. `403` with a valid session and missing ownership.

### 1.2 Ingestion: `POST /audios` + binary `PUT` (responsible area: API/DB · consumer areas: Ingestion, Web)

`POST /audios` — initial JSON body:

```json
{"subject_id": "…", "class_date": "2026-09-21", "class_timezone": "America/Bogota",
 "language_code": "es", "title": "optional", "teacher": "optional",
 "privacy_notice_version": "…", "cloud_processing_accepted": true,
 "third_party_voice_acknowledged": true}
```

The server records the user, version, timestamp, and declared providers. Missing
consent, an outdated version, or an invalid language are rejected **before** reserving capacity
or accepting bytes. The `POST` validates metadata, reserves the slot, and creates `awaiting_upload`; it does not decide
dedupe because it does not know the hash yet. It returns `201 {"audio_id", "attempt_id", "upload_url",
"upload_expires_at", "outcome":"new"}` with a relative URL, `422`, `429`, or `503`. After a
`duplicate_variant`, a second `POST /audios` includes an opaque, single-use,
short-expiry `variant_confirmation_token`; it creates another reservation and requires reupload.

`PUT /audios/{id}/content?attempt_id=…` — binary authenticated with session, CSRF, and `attempt_id`.
It computes SHA-256 incrementally and, after cleanup, decides: `202` for new admitted content,
`200 duplicate_exact` for the canonical class, or `409 duplicate_variant` with
`variant_confirmation_token`; it may also return `410 upload_expired`, `413
payload_too_large`, `415 unsupported_format`, `409 attempt_not_active`, `429`, or `503`. The
second `PUT` of a variant verifies that the hash matches the token before transcribing.
In S1 only the contract is frozen and validated; real reception and deduplication arrive in S2.

### 1.3 Shape of `outbox_events` (responsible area: API/DB · consumer area: Infra)

Fields: `id`, `tenant (user_id)`, `type`, `resource_id`, `resource_version`, `enabled`,
`blocked_reason`, `attempts`, `published_at`. Initial catalog of `type`: `index_requested`,
`analyze_requested`, `sync_task_event`, `notify`. Rule: **only IDs and non-sensitive
configuration**; never audio, tokens, or payloads. The gate is type-specific:
only `index_requested` and `analyze_requested` derived from an ingestion are born with
`enabled=false`, `blocked_reason=cleanup_pending`, and are enabled after
`cleanup_status=verified`. Calendar, notifications, and deletions are born enabled in their own
transaction after validating authorization, tombstone, and version; they do not depend on audio
cleanup.

### 1.4 Ingestion states (responsible areas: Ingestion/API · consumer area: Web)

`awaiting_upload → receiving → transcribing → transcript_committed_cleanup_pending →
succeeded`; from active states it may also end in `requires_reupload | rejected |
cancelled`. A timeout before the upload ends in `cancelled`. `cleanup_status`
(`pending|verified|failed`) is **independent** of the ASR state; an expired lease does not
prove cleanup. No final state may keep temporaries. Invalid transitions are
rejected (S2 builds the complete machine; S1 fixes the vocabulary and SSE exposure).

### 1.5 Progress SSE shape (responsible area: API/DB · consumer area: Web)

Events `snapshot` (on connect/reconnect, from the DB), `progress` (real bytes and
`done/total` fragment counts when known), `done` (final states per stage), and `error` (`code`, `detail`).
All with a monotonic `id:` header. **Never invented percentages.** `: ping` heartbeats
every ~15 s; on reconnect with `Last-Event-ID`, the server resends `snapshot` (the events
are state, not incremental).

### A1.3 — Google OAuth backend (M1)

**Depends on:** A1.2 · **Tests:** I-S1-AN-06.

How it must work:

1. `GET /auth/google/start`: generates `state` + `nonce` + `code_verifier` (PKCE), stores
   state in the ephemeral login session, and redirects to Google.
2. `GET /auth/google/callback`: validates `state`, exchanges the code with PKCE, validates
   the ID token's `nonce`/`issuer`/`audience`, extracts identity by `sub`.
3. Encrypts the Google tokens with AES-GCM (unique nonce per encryption, registered key
   version) before persisting in `google_credentials`. The tokens never leave the
   backend or appear in logs.

Acceptance criteria: real login demonstrable in compose; a reused or foreign `state` →
rejection; identity by `sub` verifiable in the DB; nothing in plaintext in the DB (test U-S1-AN-03 covers the
encryption).

### A1.4 — Opaque session, CSRF, and Origin

**Depends on:** A1.2 · **Tests:** U-S1-AN-01, U-S1-AN-02.

How it must work: issuing the `mw_session` cookie with the §1.1 attributes; storing only
the hash; expiration and revocation. `GET /me` returns the plain CSRF token in the body with
`Cache-Control: no-store`, while the DB keeps only `csrf_hash`; the token rotates with the session.
Middleware/dependency requires `X-CSRF-Token` + Origin on every mutation, including binary `PUT`.
Criteria: mutation without token or with a foreign Origin → rejection; immediate revocation after logout;
`GET /me` non-cacheable and cookies with correct flags in the observed response.

just compose: check real mounts, container limits, and absence of swap.

### S1.B2 — RAM reservation per slot

**Depends on:** S1.B1 · **Tests/evidence:** see "Mandatory verification".

How it must work: per-slot budget = original + active fragments + SDK/ffmpeg buffers +
margin. The **200 MiB / 3 h target is not approved until the test is passed**;
if it does not fit, the effective limit is lowered in capabilities with approval from the
product/operations role (never introduce disk). Product: written sizing for D4.

**Mandatory verification:** reproducible benchmark per size/duration/concurrency with
command, container/host limits, RAM/tmpfs peak, and margin; publish the table and configuration,
keeping no audio or dumps.

### S1.B3 — Supervisor, lease, fencing, and cleanup

**Depends on:** S1.B1, A1.5 (`ingestion_attempts`) · **Tests:** I-S1-SG-04/05.

How it must work: local supervisor per attempt with lease/heartbeat in the DB and a **fencing
token** per attempt; an owner with an expired lease cannot publish. Cleanup (closing
buffers/files/clients and deleting original/converted/fragments) is independent of the
ASR process: check descriptors, processes, and mounts, not just file names.

### S1.B4 — Failure matrix (9 scenarios)

**Depends on:** S1.B3 · **Tests:** I-S1-SG-04.

Scenarios demonstrated one by one with real injection: (1) success; (2) incomplete upload;
(3) format rejection; (4) timeout; (5) explicit cancellation; (6) ffmpeg/Riva/DB error;
(7) SIGKILL to the process; (8) container restart; (9) host restart — each one **during
and after the commit**. Failure = audio absent from every durable destination + coherent states.

### S1.B5 — Audio absence verification

**Depends on:** S1.B3 · **Tests:** I-S1-SG-06.

How it must work: after each scenario, inspection of disk (all mounts), Redis
(key values), logs, traces, and caches looking for the original, converted files, and fragments.
Evidence saved without audio (command captures and boolean results, never dumps).

### S1.B6 — Expired lease and blocked outbox

**Depends on:** S1.B3 · **Tests:** I-S1-SG-05.

How it must work: an expired lease does **not** mark cleanup verified (only cleanup
evidence does); without evidence, the outbox stays blocked; a cleanup failure stops
admitting new uploads and triggers an alert. This contract is the gate S2 will
implement definitively (A2.10/J2.1).

## 7. Integrated flow of the week

1. **Login (minimal E2E):** browser → Caddy → `GET /auth/google/start` → Google →
   callback → `mw_session` session issued → non-cacheable `GET /me` returns profile + CSRF.
2. **Ingestion contract (skeleton):** `POST /audios` (metadata → relative URL) →
   binary `PUT` → in S1 it validates session, CSRF, attempt, expiration, and declared size and
   responds `503 capacity_unavailable` without reading the body; the `202` arrives in S2 with
   tmpfs reception and the commit (an acceptance that would discard the audio is not simulated).
3. **Compose topology:** Caddy fronts web/api/ingest on the same origin; api ↔ Postgres
   pgvector + Redis; worker/scheduler ↔ Redis; ingest isolated and hardened with no provider
   access from `/readyz`.
