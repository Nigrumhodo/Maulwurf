## 0. Objective and exit gate

**Objective:** opt-in Gmail with reliable reminders and digests, complete dashboard with
Ctrl+K, final hardening (security, load, restore, deployment), and the final demo.

**Exit gate — the sprint does NOT close without all of this:**

1. **Observed real test send** with an authorized account (P-S4-JF-07) and subsequent
   cleanup; Gmail is **opt-in** and only sends to the user's verified email.
2. Reminder dedupe, DST (nonexistent/repeated hour), and `delivery_unknown` tested —
   **no automatic retry** on uncertain delivery.
3. Restore verified: D8 was already approved before non-synthetic data; only encrypted
   text/metadata and deleted items do not reappear.
4. G7-MAIL and G8 closed; G3 revalidated with a sweep. Builds/tests of the 3 apps,
   reminders within the 15-minute target, and budget/alerts active.
5. Reference deployment with versioned images, migration as a single job, and **rollback
   tested**.
6. Complete dashboard + Ctrl+K; final demo rehearsed ×2 (Thursday and Friday).
7. Runbooks published and a real cost table; security checklist and PLAN_IMPLEMENTACION §9
   marked with evidence.

**Interfaces frozen on Monday:** preferences/notifications (`settings`, `notifications`,
dedupe); final UI routes.

## 1. Frozen contracts (exact reference)

### 1.1 `notifications` (M8) — provider: API/DB · consumers: Infra, Web

Fields: `scheduled_at`, `due_version`, `dedupe_key`, `status`
(`pending|sending|sent|failed|delivery_unknown|cancelled`), `sent_at`,
`provider_message_id`, attempts, and a **redacted error** (no PII or payload). An expired
`sending` lease → **`delivery_unknown`** (uncertain delivery), **not** automatically
pending or system-retryable. `dedupe_key` = `(user_id, type, task_id,
due_version, occurrence)` — uniqueness prevents duplicates **by construction**.

### 1.2 Reminder scheduling — provider: Infra

Timed (with hour): **T-48 h / T-24 h / T-2 h**. All-day: **T-3 d / T-1 d** at the user's
local time. No date → no reminders. Never a retrospective burst: changing the due date or
preferences cancels **only** the obsolete future occurrences. DST: nonexistent hour → next
valid instant; repeated hour → a single notification.

### 1.3 Preferences and M8 endpoints — API/DB area

`PATCH /me/notifications` (Gmail opt-in, digests, and thresholds) ·
`POST /notifications/test`
(send to the verified email; `202` with a warning) ·
`GET /notifications?status=&from=&to=&limit=&cursor=` ·
`POST /notifications/{id}/resend` with `{acknowledge_duplicate_risk:true}`. Resending creates
a **new** audited occurrence and never mutates `delivery_unknown` to `pending`.
`DELETE /me` returns `deletion_operation_id`; `GET /me/deletion/{id}` exposes the closure
without profile data.

### 1.4 Digests — provider: Infra

Daily digest (07:00, configurable by local date) and weekly (Sunday) with the week's
conflicts (`time_conflicts` + `deadline_clashes` from the M5 contract). One digest = one
notification with its `dedupe_key` (includes the digest's local date).

## 2. API/DB tickets (`A4.x`)

### A4.1 — `notifications` + `settings` extension

**Depends on:** A3.8 · **Tests:** U-S4-AN-01/02.

`settings` already exists in S3 for Calendar; this migration only adds Gmail opt-in,
digests, and thresholds. `notifications` implements statuses, lease, persistent dedupe, and
redacted errors. `dedupe_key` uniqueness lives in the DB; do not create a second settings
table.

### A4.2 — Preferences, test, and resend endpoints

**Depends on:** A4.1 · **Tests:** I-S4-JF-05.

Implements `PATCH /me/notifications`, `POST /notifications/test`, the cursor-paginated
listing, and `POST /notifications/{id}/resend` with mandatory acknowledgement. The test uses
the real/controlled-double pipeline; resend creates a new row and leaves the original
uncertainty intact.

### A4.3 — Cancellation of obsolete occurrences

**Depends on:** A4.1 · **Tests:** U-S4-AN-03.

How it must work: when the due date (new `due_version`) or preferences change, **only** the
obsolete future occurrences are cancelled (`status → cancelled`); already-sent ones stay as
they are; **never** a retrospective burst when confirming late.

### A4.4 — Account deletion

**Depends on:** A3.8, J3.3 · **Tests:** I-S4-AN-04.

`DELETE /me` creates `account_deletions`, responds `202 {deletion_operation_id}`, applies
the tombstone, and blocks sessions/jobs. If event deletion was authorized, run/queue the
remote step before revoking tokens; then purge data and derivatives.
`GET /me/deletion/{id}` returns `pending|completed|completed_with_remote_failures`; the
residual record keeps no profile, text, or tokens. Double execution is idempotent.

### A4.5 — Backup and restore validation (D8 already approved)

**Depends on:** A4.4, D8 approved · **Tests:** I-S4-AN-05.

The D8 policy is approved before non-synthetic data; this ticket validates backups of
encrypted text/metadata only, the agreed retention, and tombstone reapplication on a clean
restore. It never introduces audio or reopens the decision by default.

### A4.6 — Final hardening

**Depends on:** A4.4, J4.2 · **Tests:** I-S4-AN-06.

Ownership verified in API/SSE/tools/jobs; `no-store` on private responses; basic rate limits
with `429/503` and correct headers (`Retry-After`) on sensitive endpoints (auth, upload,
chat, integrations). No invented numbers: limits per documented decisions.

### A4.7 — Final G3 + orphan sweep

**Depends on:** A4.4 · **Tests:** I-S4-AN-07.

Full isolation suite (B accesses nothing of A on any channel) + a sweep verifying
**zero** chunks/embeddings/derived rows without a class after the deletions.

### A4.8 — Demo rehearsal support

**Depends on:** — · **Tests:** — (demo support: evidenced with E-S4-DA-04).

Be available during the Thursday/Friday rehearsals to unblock live; demo without dead ends.

## 3. Infra/Integrations tickets (`J4.x`)

### J4.1 — Opt-in Gmail with `gmail.send`

**Depends on:** D7-MAIL, authorized credentials · **Tests:** U-S4-JF-03, P-S4-JF-07.

How it must work: incremental OAuth adding `gmail.send` only if the user enables the option
(opt-in in `/settings`); recipient **fixed to the account's verified email**; HTML +
plain-text templates **escaped**; no mail GET mutates state; "Snooze" in the email is a link
to the authenticated UI (never an action by email). No search or inbox reading.

### J4.2 — ARQ scheduler with a single role

**Depends on:** A4.1 · **Tests:** I-S4-JF-04.

How it must work: native ARQ cron scheduler with **a single active role** (elected via a DB
lease); every minute it computes due dates/local times and **claims rows atomically**;
multiple workers protected by uniqueness (`dedupe_key`) and leases; target delivery SLA
within 15 min (not second-level accuracy).

### J4.3 — Reminder scheduling

**Depends on:** J4.2 · **Tests:** U-S4-JF-01.

How it must work: when a task is confirmed, schedule T-48/T-24/T-2 h (timed) or
T-3d/T-1d at local time (all-day) per §1.2; task without a date → no reminders;
occurrences are inserted with their exact `dedupe_key`.

### J4.4 — Persistent dedupe + DST

**Depends on:** J4.3 · **Tests:** U-S4-JF-02.

How it must work: `dedupe_key` uniqueness makes duplication impossible by construction;
changing the due date/preferences cancels obsolete occurrences (contract A4.3); DST:
nonexistent hour → next valid one; repeated hour → **a single** notification. Test cases
with injectable clocks crossing the time change.

### J4.5 — Uncertain delivery handled

**Depends on:** J4.2 · **Tests:** I-S4-JF-05.

How it must work: lost response or expired lease → `delivery_unknown`, **no automatic
retry**. The panel explains the risk; resend requires acknowledgement and creates a new
notification with audited dedupe_key/occurrence without changing the original. Gmail does
not offer exactly-once.

### J4.6 — Digests

**Depends on:** J4.2 · **Tests:** I-S4-JF-06.

How it must work: daily at the configured hour by local date (07:00 default) and weekly on
Sunday; content: upcoming tasks + the week's conflicts; one send per user and period with a
`dedupe_key` that includes the local date; respects opt-in.

### J4.7 — Reference deployment

**Depends on:** J1.1 · **Tests:** L-S4-JF-08.

How it must work: ARM host + domain + tunnel per the infrastructure proposal;
**versioned** images (immutable tag per release); Alembic runs as a **single job**
(no concurrent migrations); **rollback tested** (back to the previous image and migration in
a documented rehearsal); read-only root fs and tmpfs per the F0.2 hardening.

### J4.8 — Alerts, budget, and runbooks

**Depends on:** J4.7, S4.1, A4.5 · **Tests:** C-S4-JF-10.

Budget/alerts: LLM tokens, ASR minutes, Google quotas. Executable runbooks for
cleanup/recovery, provider outage, revoked tokens, restore, and account deletion.
**Mandatory verification:** run each runbook in the reference environment and record
command, result, and redacted evidence in C-S4-JF-10.

### J4.9 — G8 closure

**Depends on:** J4.2, J4.7, J4.10, A4.5, S4.3, L4.1 · **Tests:** E-S4-JF-09.

Builds/tests of the 3 apps green; restore verified; reminders within the target (≤15 min)
with healthy dependencies (PG/Redis/provider).

### J4.10 — Observed real Gmail send

**Depends on:** J4.1; authorized account · **Tests:** P-S4-JF-07.

How it must work: one controlled end-to-end run with the protected account: test reminder +
test digest; evidence of the send (no PII); **post-run cleanup** of test resources;
documented budget.

## 7. Integrated weekly flow (happy path)

1. **Reminder:** confirmed task (S3) → J4.3 schedules occurrences with `dedupe_key` →
   scheduler J4.2 claims at local time → Gmail send J4.1 → `sent` or `delivery_unknown`
   (J4.5) → D4.2 panel.
2. **Digest:** scheduler J4.6 computes by local date → task + conflict content →
   single send with opt-in respected.
3. **Global lookup:** Ctrl+K (D4.3) → `GET /search` → reader with segment.
4. **Closure:** S4.1 runbooks + J4.8 alerts + A4.5 restore + J4.7 rollback + S4.5 costs →
   L4.2/L4.3 checklist → J4.9/D4.7 demo.

## 9. Plan Bs

- **Gmail without an authorized account in time:** J4.1 is developed with a local double (a
  test SMTP server that responds like Gmail) and the real send `P-S4-JF-07` stays as a
  **non-negotiable** closure condition — if it does not happen, S4 does not close and this
  is communicated explicitly.
- **Restore reveals deletion leaks:** stop the reference deployment until tombstones are
  reapplied correctly; G8 does not close with a failed restore.
- **PWA without slack:** it moves down to the F4 backlog (it is marked optional in the plan).
- **Rollback fails in the rehearsal:** fix and repeat before the demo; the demo runs on
  the reference deployment only with a tested rollback.
