## What is being measured

The contract limit is what `GET /ingestion/capabilities` publishes and the API enforces.
It is still `null` while `limits_validated=false` (D4 is not approved), so the API uses its
provisional `upload_max_bytes = 209,715,200` (200 MiB). Caddy is the outer envelope:

| Scope | Caddy value | Bytes / duration |
|---|---|---|
| `PUT /audios/*/content` | `request_body { max_size 220MB }` | 220,000,000 bytes (decimal `MB`) |
| JSON API routes | `request_body { max_size 10MB }` | 10,000,000 bytes |
| All requests | `servers.timeouts.read_body` | 20m |
| All requests | `servers.timeouts.read_header` | 30s |
| All requests | `servers.timeouts.write` | 0 (no total deadline; SSE) |
| All requests | `servers.timeouts.idle` | 5m |

The upload ceiling is deliberately above the API limit: a body between 200 MiB and 220 MB
is read by the API and rejected with the structured `413 payload_too_large` envelope.
Bodies above 220 MB are stopped by Caddy with a plain `413`. The `@api` value is an abuse
guard for JSON, not a second contract.

## Observed status codes

| Case | Bytes | HTTP | Sink outcome |
|---|---|---|---|
| 1 MiB upload | 1,048,576 | `202` | `received 1048576 bytes` |
| Exactly `request_body.max_size` | 220,000,000 | `202` | `received 220000000 bytes` |
| One byte over the upload ceiling (streamed) | 220,000,001 | `413` | no line (not proxied) |
| One byte over the `@api` 10 MB ceiling | 10,000,001 | `413` | not proxied |
| `read_body=2s`, 10 × 64 KiB over 5 s | 640,000 attempted | `000` (curl rc 55) | no line (not proxied) |

The slow case is the same Caddyfile with `read_body 2s`; the access log records
`bytes_read=262144`, `duration=2.0008s`, `status=0`. With the production `read_body 20m`
the 5-second upload is not cut.

Buffering checks after the 220 MB case:

| Check | Result |
|---|---|
| New files in the proxy (excluding `/data`, `/config`, certificates and PKI) | none |
| Deleted file descriptors (possible spool) | 0 |
| Request bodies in the access log (`BEGIN`, `Content-Disposition`, `filename=`) | 0 |
| Caddy peak RSS (`VmHWM`) | 44,176 kB |

A 220 MB whole-body buffer would be visible as a peak RSS above 220 MB; 44 MB is the
normal Caddy baseline plus TLS state. Caddy `request_body` wraps the request in
`http.MaxBytesReader` and the reverse proxy streams it; it does not spool.

## Static regression

```text
$ python3 scripts/ci/check_caddy_limits.py
Caddyfile: infra/Caddyfile
servers.timeouts: read_body=1200s read_header=30s write=0s idle=300s | @upload max_size=220000000 | @api max_size=10000000 | API provisional=209715200
OK: C-S2-JF-13 static checks passed.
```

The check fails if the upload ceiling drops to or below the API provisional limit, if the
`@api` ceiling is not lower than the upload one, if a timeout disappears, if `read_body`
is shorter than the API upload window, if `write` becomes finite (SSE), or if `admin off`,
`tls internal` or the `/internal/*` 404 is removed.

## Findings

- **Caddy does not pre-reject a declared `Content-Length`.** `request_body` only wraps the
  reader; a request that claims a huge length but sends no bytes is not answered until the
  body read times out or the upstream reads. The script therefore streams real synthetic
  bytes for the over-limit cases. The API keeps its own header check before reading, so a
  real client with a declared oversized body still gets the API envelope up to the Caddy
  ceiling; a lying client is bounded by `read_body`.
- **The edge ceiling is not the contract.** The published limit remains
  `capabilities.max_upload_bytes` (`null` until D4). If D4 publishes a limit above 220 MB,
  the Caddy ceiling must move in the same revision; if it publishes a lower limit, the API
  and UI already enforce the lower value and Caddy stays a safety net.
- **No L7 bot/DDoS protection.** Dropping Cloudflare also drops its bot protection. That is
  a deployment concern (J4.7), not an S2 capability; no document should claim it.
- **SSE and `write`.** `write 0` is intentional. A finite total write timeout would cut
  `/audios/*/progress` for long classes; the route already uses `flush_interval -1`.
