Review fix1 (hoplite findings, 2026-10-31)
------------------------------------------
Reproduced on the pre-fix code (head 0c2626c) with the new tests: 9 cases failed. The key
one, `test_an_event_reprogrammed_from_outside_the_window_updates_in_place`, raised
`sqlalchemy.exc.IntegrityError: duplicate key value violates unique constraint
"uq_calendar_events_user_id_calendar_id_event_id"`; the same test passes with the fix.

Corrections:
1. [ALTA] `SqlCalendarMirror.replace_window` now upserts on `(user_id, calendar_id,
   event_id)` (`ON CONFLICT DO UPDATE`) and prunes rows of the republished calendars that
   ended before the window. `source` and `task_id` are preserved on conflict and
   task-linked rows are never pruned (the write path owns them).
2. [MEDIA] `_resolve_window` completes a lone bound from the bound actually sent
   (`from` -> `from+60`, `to` -> `to-7`), so `GET /calendar/events?from=<today+90>` answers
   200 with that window instead of a misleading inverted-range 422.
3. [BAJA-MEDIA] The per-user advisory lock uses the two-int form with namespace `0x4D57`,
   the same value as `services/audios.py` (A2.14), instead of a bare bigint key.
4. [ROBUSTEZ] `GoogleCalendarEventSource` rejects a non-object Google payload with
   `CalendarEventInvalid("events_payload_invalid")` instead of an `AttributeError` -> 500.

Secondary, low risk: `CalendarService.page` documents the expected read bound (not
paginated; width <= 366 days; no silent LIMIT that would hide rows), the event `timeZone`
is validated before storing, and the `_dedupe` docstring states the real rule (last
occurrence in read order wins).

Review fix2 (hoplite finding on head b8f7c0b, 2026-10-31)
--------------------------------------------------------
Finding: `SqlCalendarMirror.replace_window` deleted every window row without excluding the
task-linked ones. The upsert that followed re-inserted the row without `task_id` (the
inserted values never carry it), so every refresh silently unlinked the task and freed the
partial unique index `calendar_events_one_link` (one linked event per task).

Reproduction on the pre-fix head b8f7c0b (only the fix stashed, new tests applied):
$ ... uv run pytest tests/integration/test_calendar_read.py -q -k "task_linked"
2 failed, 15 deselected
  test_a_task_linked_row_inside_the_window_keeps_its_link_across_refreshes
  test_a_task_linked_row_inside_the_window_survives_a_refresh_without_it

Decision (recorded in the `replace_window` comment and the module docstring): the read
mirror never deletes nor unlinks a task-linked row. If the linked event disappears from
Google or moves out of the window, the row is deliberately kept inside the mirror; the
write path (J3.4/A3.8) owns those rows and is the only place allowed to reconcile or unlink
them.

Fix: the window delete adds `CalendarEvent.task_id.is_(None)`, the same rule the pre-window
prune already used. The `ON CONFLICT DO UPDATE` SET list still omits `task_id` (and
`source`), so an upsert over an existing linked row only refreshes the remote values.

Review fix3 (hoplite findings on heads 3faa571/644c109/2e1753c, 2026-10-31)
----------------------------------------------------------------------------
1. [media-alta] A calendar removed from the read selection kept its rows forever and
   `GET /calendar/events` still returned them: `replace_window` only pruned the calendars
   being republished, and `page` filtered by user and window only.
   Fix: `CalendarService.page` now filters by the current `calendar_read_calendar_ids`
   (an empty selection returns no rows), so a deselection is effective immediately; and
   `SqlCalendarMirror.replace_window` reads the previous coverage inside the same
   savepoint and deletes the unlinked rows of every calendar that was in it and is no
   longer selected. Task-linked rows are still never deleted or unlinked.
   New case: `test_a_deselected_calendar_stops_being_returned_and_is_pruned_on_refresh`
   (GET hides the deselected calendar before the refresh; the refresh prunes its unlinked
   row, keeps the linked one, records the new coverage and answers coverage_ok=true).
   Updated case: `test_get_reports_never_synced_and_changed_coverage` now expects no
   events after the selection changes instead of returning the old mirror.
2. [media-alta] A task-linked row inside the window that Google no longer returns kept
   `remote_status='confirmed'`, so GET presented it as a current event.
   Fix: before the upsert, linked rows of the republished calendars that overlap the
   window are marked `remote_status='missing'` (task_id untouched); every event that did
   arrive is rewritten by the upsert, so only the really absent ones stay `missing`.
   Rows outside the window are not touched (the read never observed them).
   Updated case: `test_a_task_linked_row_inside_the_window_survives_a_refresh_without_it`
   asserts the row survives with task_id, is returned as `missing`, and returns to
   `confirmed` when Google returns the event again.
3. [medio] A cancelled linked event kept `confirmed` because `parse_remote_event` dropped
   cancelled instances with `None`.
   Fix: a cancelled item is returned as `RemoteCancelledEvent` (a key, no block parsed);
   `CalendarRead` carries both active events and cancelled keys; `replace_window` marks
   the matching rows `remote_status='cancelled'` keeping task_id (deleting them would free
   `calendar_events_one_link`). A known cancellation is not downgraded to `missing` by a
   later read that simply does not return the event; a read that returns it rewrites the
   status from Google.
   New case: `test_a_cancelled_task_linked_event_is_marked_cancelled_and_keeps_the_link`
   (mirror and GET show `cancelled` with task_id, stays cancelled on an absent refresh,
   returns to `confirmed` when Google returns it).
   New unit cases: cancelled keys are exposed by the adapter and deduplicated/forwarded to
   the mirror.
