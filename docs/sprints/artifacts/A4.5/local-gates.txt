What I-S4-AN-05 proves
----------------------
- The backup emits an OpenPGP AES-256 dump and deletion log plus a SHA-256 manifest; the
  transcript/message markers are not present in the encrypted bytes and the dump does not
  start with the plaintext `PGDMP` signature.
- The dump is taken before deleting an account and tombstoning a class, a subject and a
  conversation. After restoring into a second, empty database and replaying the exported
  deletion log:
    * the deleted account is `deleted` with `deleted-<id>@invalid` / `deleted:<id>`
      placeholders, every tenant table for it is empty and the residual
      `account_deletions` row keeps the original operation id and `completed` status;
    * the tombstoned class keeps `deleted_at` with `active_transcript_version = NULL` and
      loses its transcripts/chunks; its marker text is gone;
    * the tombstoned conversation keeps its tombstone with a NULL title and no messages;
    * the tombstoned subject keeps its `deleted_at`;
    * the retained class, transcript, chunk, message and active user survive unchanged.
- The manifest pins the D8 30-day retention, which equals `RESIDUAL_RETENTION_DAYS`; a
  manifest older than 30 days is refused, and `prune` removes only the stale file.
- `verify` accepts the intact dump+deletion-log pair and refuses a tampered deletion log
  (the manifest carries both SHA-256 values).
- A second restore into the already-populated target is refused (`not clean`), so the
  destructive path cannot overwrite a database by mistake.
- A new `bytea` column outside the Google token blobs aborts the backup, pinning the
  no-audio contract as a fail-closed schema check.
- The only `bytea` columns in the restored schema are
  `google_credentials.access_token_enc` and `refresh_token_enc` (AES-GCM blobs).

What the new I-S4-AN-05 cases prove
-----------------------------------
- Restore without a log and without the opt-in stops before pg_restore; the target keeps
  zero application tables.
- Restore with `--allow-missing-deletion-log` emits a WARNING on stderr and the success
  line says that no deletion log was replayed.
- A valid deletion log taken from another backup is rejected by checksum before anything is
  decrypted or written; the target keeps zero application tables.
- `verify` fails with a WARNING when the manifest pins a log that is not next to the dump;
  the opt-in keeps the warning and verifies the dump alone.
- The default restore uses the paired log, and an explicit copy of the pinned log also
  works.
- Carol, tombstoned with a bare `users.status` change and no `account_deletions` row, is
  purged by the log's `users` array: `deleted` placeholders, zero tenant rows, no text.
- A post-deletion log is attached with `export-deletions --refresh-backup`, which replaces
  the paired log and re-pins `deletion_log_sha256`; the restore of the older dump then
  re-applies the later deletions.
