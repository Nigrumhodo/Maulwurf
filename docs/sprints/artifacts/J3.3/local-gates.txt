## Review fix1 (2026-10-31, second hoplite review of head `7bf4d0a`)

Scope: the three findings of the read-only review.

1. **Duplicate-calendar race (blocking).** `connect_calendar` now takes a
   transaction-scoped advisory lock keyed by the user
   (`pg_advisory_xact_lock(hashtextextended('calendar_binding:<user_id>', 0))`) before
   reading the stored ID and before list/create. Two concurrent callbacks for the same user
   take turns; the second reuses the ID the first committed. The `ON CONFLICT` upsert stays
   as the convergence point for the stored ID. Regression
   `test_two_concurrent_connects_create_a_single_calendar` uses two real DB sessions and a
   `threading.Barrier` inside the list call, so without the lock both callbacks list an
   empty calendar list and both `POST /calendars`. Verified red without the lock (the single
   `POST` assertion fails) and green with it.
2. **Non-owned calendar adoption (blocking).** `is_maulwurf_calendar` and the stored-ID
   reuse path now require `accessRole == 'owner'` and `primary` not true. The stored ID is
   revalidated with `GET /users/me/calendarList/{id}` (`get_calendar_list_entry`), because
   the plain Calendar resource does not expose `accessRole`. A shared/subscribed copy is
   skipped and an owned calendar is created instead. Unit cases cover reader, writer,
   freeBusyReader and a missing role; the integration case
   `test_connect_never_adopts_a_read_only_maulwurf_lookalike` proves the HTTP flow.
3. **`ON CONFLICT` without real-table coverage.** The `outbox_events` half is now validated
   against the real schema.
   `test_sync_task_event_conflict_target_matches_the_real_unique_index` checks the `0001`
   unique index definition (four columns, `NULLS NOT DISTINCT`, no partial predicate) and
   runs the exact `INSERT ... ON CONFLICT (...) DO NOTHING` twice: the first returns a row
   and the identical second one is swallowed by the index. The `UPDATE tasks ... RETURNING`
   statement still has no real table in `develop`; `calendar_resume.py` records it as
   pending A3.1 and no test claims otherwise.
