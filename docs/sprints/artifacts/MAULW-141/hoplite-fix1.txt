## The three fixes

1. `schedule_task_reminders` now upserts with `ON CONFLICT ON CONSTRAINT
   uq_notifications_dedupe_key DO UPDATE ... WHERE notifications.status = 'cancelled'`.
   A repeated confirmation of the same `due_version` leaves `pending` rows untouched and
   re-arms only rows A4.3 cancelled, resetting `lease_expires_at`, `attempts`,
   `claimed_by_fence`, `sent_at`, `provider_message_id` and `last_error_code`. `sending`,
   `sent`, `failed` and `delivery_unknown` never match the reopen condition. `inserted`
   counts rows armed by the attempt (new rows plus reopened cancelled rows).
2. `_database_clock` uses `func.clock_timestamp()` (the statement instant) instead of
   `func.now()` (transaction start). J4.2's scheduler keeps `now()` on purpose: its bounded
   tick needs one shared instant for election, expiry and claim, and both expressions are
   the same database server clock.
3. The conflict target is explicit (`uq_notifications_dedupe_key`); any other unique
   violation now surfaces instead of being absorbed.

## PostgreSQL adapter

```text
$ uv run pytest tests/integration/test_reminders_schedule.py -q
12 passed
```

The three new cases are:

- `test_a_preference_cancelled_reminder_is_rearmed_by_the_same_confirmation`: disable T-48,
  re-enable it, confirm the same `due_version`; the same row returns to `pending` with its
  delivery fields cleared and the other two thresholds stay untouched.
- `test_a_delivered_or_in_flight_occurrence_is_never_rearmed`: a `sent` T-48 and a `sending`
  T-24 are not rewritten by the repeated confirmation; only the still-pending T-2 stays.
- `test_the_adapter_clock_is_the_statement_instant_not_the_transaction_start`: a 250 ms
  `pg_sleep` plus a T-48 threshold placed 50 ms before the statement instant proves that a
  stale `now()` would arm the occurrence and `clock_timestamp()` skips it.
