This review closes the three hoplite findings on `e1d6d00`:

1. **H1 (critical):** `task_sources` could cite a segment of another transcript of the same
   user, and neither `audio_id` nor `transcript_version` was tied to the cited transcript.
   New migration `0012_s3_task_source_membership` (not an edit of `0002`/`0011`, both already
   applied in the chain) adds `segments (user_id, transcript_id, id)` and
   `transcripts (user_id, audio_id, id)`, and replaces the two 2-column FKs with
   `(user_id, audio_id, transcript_id)`, `(user_id, transcript_id, transcript_version)` and
   `(user_id, transcript_id, segment_id)`. Real-database cases: a source that mixes
   transcript A with segment B, a wrong `audio_id` and a wrong `transcript_version` are each
   rejected with `IntegrityError`.
2. **H2 (contract decision):** `UNIQUE (task_id, base_task_version, revision_type, run_id)`
   stays NULL-distinct. Several pending `edit_of_confirmed` proposals may share a base
   version; only the explicit confirm promotes one and bumps `tasks.version`, so the rest
   answer `409 version_conflict`. The decision and the `NULLS NOT DISTINCT` alternative are
   recorded in `docs/ESPECIFICACION.md` §M4 and `docs/DISENO_BD_API_SPRINTS.md` §2.8; a
   repeated reanalysis of the same run is still rejected (existing integration case).
3. **H3 (inbox + purge):** `tasks_inbox_status (user_id, status)` serves the
   `ambiguous`/`missing` tray (both due columns are NULL, so the partial due indexes cannot).
   The class tombstone now deletes `task_revisions`, `task_sources` and `tasks` before
   `segments`/`transcripts`, and the `202` body reports `tasks_deleted`,
   `task_sources_deleted` and `task_revisions_deleted`. Before this fix the purge failed with
   `Key (user_id, id)=… is still referenced from table "task_sources"`; the new regression
   seeds a task, a source and a revision in the class and asserts every count in
   `test_delete_purges_every_derivative_and_keeps_google_by_default`.
