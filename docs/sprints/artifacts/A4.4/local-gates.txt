What the new evidence proves
----------------------------
- A purge exception after the durable tombstone: the router logs only the operation id and
  returns 202; the operation is left `pending` with `claimed_at = NULL`. The resume route
  (restricted initiator cookie + Origin/CSRF, owner-scoped) completes it, and the fake
  Calendar transport receives no second DELETE for the already-succeeded event.
- A process crash after the atomic claim: a stale `running` row with `claimed_at` older than
  the 1 h lease is reclaimed by the same resume route and reaches `completed`.
- Concurrent executions on independent PostgreSQL connections: the second caller returns
  `running` without running the purge or the remote step; the operation ends `completed`
  with `attempts = 1` and each `google_remote_operations` row keeps `attempts = 1`.
- Retention: expired rows of `account_deletions` and `google_remote_operations` are deleted
  in batches of one (1/1, 1/1, 0/0) while the unexpired row survives, executed as
  `maulwurf_jobs` with `app.cross_tenant = on` under forced RLS.
- `google_remote_operations.expires_at` equals the owning `account_deletions.expires_at`.
- Docs: the spec and implementation plan record the applied retention and the
  `delete_maulwurf_events=false` default (Maulwurf-created Google events stay unless the user
  opts in).
