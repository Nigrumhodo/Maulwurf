This review closes the confirmed medium finding and the three low findings on `e041055`:

1. **`E'\v'` is not a vertical tab in PostgreSQL.** In an escape string, `\v` is not a
   recognized escape; it is the letter `v`. The previous
   `btrim(value, E' \t\n\r\f\v')` therefore:
   - treated `'v'` and `'vvv'` (valid base32hex Google event ids) as blank, so the CHECKs
     rejected them and the `0013` cleanup would drop or reject them; and
   - let a real vertical tab (`chr(11)`) pass every CHECK and survive the cleanup, contrary
     to the documented "ASCII whitespace including vertical tabs" criterion.

   Reproduced on PostgreSQL 16.15 before the fix:

   ```
   SELECT btrim(E'\v', E' \t\n\r\f\v') = '';    -- true (E'\v' is the letter v)
   SELECT btrim(E'\x0b', E' \t\n\r\f\v') = '';  -- false (real VT not stripped)
   SELECT encode(convert_to(E'\v', 'UTF8'), 'hex'); -- 76 = 'v'
   ```

   The helper now uses an explicit, escape-independent character set:
   `btrim(value, E' \t\n\r\f' || chr(11)) = ''`. `chr(11)` is IMMUTABLE (`pg_proc`), so the
   SQL function stays eligible for use in CHECKs. After the fix:

   ```
   SELECT btrim(E'\x0b', E' \t\n\r\f' || chr(11)) = ''; -- true
   SELECT btrim('v', E' \t\n\r\f' || chr(11)) = '';     -- false
   SELECT btrim(E'\u000b', E' \t\n\r\f' || chr(11)) = ''; -- true
   ```

   The `0013` module docstring, `_create_blank_helpers` docstring, `app/models/settings.py`
   and `app/models/calendar_event.py` now describe the real criterion (space, tab, newline,
   carriage return, form feed and vertical tab) and explain why `chr(11)` is used.

2. **Python and database criteria agree on the vertical tab.** `parse_remote_event` uses
   `str.strip()`, which already removes `\x0b`; the SQL helper now does the same. The ETag,
   remote-status and event-id paths share the criterion, and the code notes that
   `str.strip()` covers the SQL helper's ASCII set.

3. **The `settings.py` docstring is correct.** It no longer claims that blank is plain
   `btrim(value)` (which only strips spaces); it states the explicit ASCII whitespace set
   and the exact SQL expression.

4. **Regression tests.** `tests/unit/test_calendar_read.py` now covers a vertical-tab ETag,
   status and event id, accepts `'v'`/`'vvv'` as non-blank identity/status/ETag, and asserts
   that a padded event id is stored trimmed.
   `tests/integration/test_calendar_settings_mirror.py` adds `chr(11)` (alone and padded) to
   the blank rejection matrices for the settings columns and the mirror fields, plus two
   positive cases proving that `'v'`/`'vvv'` are accepted and persisted in the write/read/
   coverage calendars and in `calendar_id`/`event_id`/`remote_status`/`etag`.
   `tests/integration/test_migrations.py`:
   - the legacy round trip seeds an ETag made only of `\x0b` (becomes NULL) and an event
     whose `calendar_id`/`event_id` are `'vvv'`/`'v'` (survives the upgrade and the CHECKs),
     while `'v'` array elements are kept and a `chr(11)` array element is removed;
   - the rejection matrix adds `chr(11)` for `calendar_id`, `event_id` and `remote_status`.

5. **The event id is persisted exactly as validated.** `parse_remote_event` now assigns
   `raw_id.strip()` to `event_id` and uses it for both the normal and the cancelled key, so
   a padded remote id cannot create a second mirror row when Google later returns the
   canonical id.
