## Review rework (hoplite, 2026-11-01T13:39:11Z)

PR #156 is reused (no new PR). Two critical findings fixed on `task/MAULW-144`:

- **CRITICAL 1 — a pending digest of the current period could fire with the old
  schedule.** `_cancel_stale_digests` only cancelled rows whose `occurrence` was older than
  the local day/week; a change of `digest_daily_time` to an hour already passed today (or
  of `digest_weekday` to a day already passed this week) moves the planner to the next
  period and leaves the current row pending with the old `scheduled_at`. The new
  `_cancel_unscheduled_digests` compares the pending row with the plan: an older-period row
  of an enabled type is cancelled when its `scheduled_at` is still ahead (the reported case)
  or when its period is over (the pre-existing outage rule). A current-period row whose
  instant already arrived stays claimable by J4.2, so a missed claim at the exact minute is
  retried later the same day as before, and a pre-armed row of a later period is left for
  the plan to adopt instead of being cancelled and recreated.
- **CRITICAL 2 — the upsert rewrote every pending row each tick.** `_write_occurrences`
  applied `_rearmed_values` to every `pending`/`cancelled` row without comparing
  `scheduled_at`, so each minute rewrote all pending rows (and counted them in `written`).
  The conflict `WHERE` now updates only a `cancelled` row or a `pending` row whose
  `scheduled_at` is distinct from the planned one, so a no-change tick reports `written=0`,
  and `attempts` is no longer in the update set.

**Retry contract checked before accepting the behavior (M8 / J4.2).** `claim` increments
`attempts` once when `pending → sending`; `sending` only transitions to
`sent`/`failed`/`delivery_unknown`; all of them are terminal and an expired lease becomes
`delivery_unknown` (`apps/api/app/services/notifications.py`). A manual resend creates a new
row with `occurrence_seq > 0` and never mutates the original
(`apps/api/app/services/notification_center.py`). Therefore J4.2 never returns a row to
`pending` with `attempts > 0`, so the reset was not an active bypass through the public
core; it was still an unconditional per-tick rewrite that would erase the counter of any
pending row carrying a retry. Fixed as described (no rewrite without a change, `attempts`
preserved).
