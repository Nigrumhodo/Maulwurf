What the new evidence proves
----------------------------
- `NoStoreMiddleware` rewrites the header on every HTTP response, including a route that
  tries to set `Cache-Control: public`, redirects, framework 404/405 and rate-limit
  rejections; `_response` repeats it for the unhandled 500 built outside the user
  middleware. The progress SSE is no-store and foreign ids answer 404 before streaming.
- The fixed-window limiter allows exactly `limit` requests in a window and rejects the next
  with `429 rate_limited`, `Retry-After` and `{limit, window_seconds, scope}`; identities,
  scopes and windows are independent; a Redis failure answers `503 capacity_unavailable`
  with `Retry-After` without leaking the identity.
- The auth limiter is keyed by a SHA-256 of the peer address (no raw IP in Redis) and the
  consent limiter by the authenticated user; an unset limit returns before touching Redis.
  Both are documented as configuration because D4/D5 publish no number.
- Chat (two-stream M7), search (provisional 30/min M6/D5), upload (A2.3/A2.14) and the
  Calendar cooldown (M5) are the documented active limits; every rejection carries
  `Retry-After` and `no-store`.
- `index_job.revalidate` returns no owner for a tombstoned class or a revoked user, so a
  queued job cannot index a deleted/foreign resource.
- `apps/web` is untouched and no secret, audio or provider credential was handled.
